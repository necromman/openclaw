# IX-Auth 인가(Authorization) 모델 설계

> **작성**: 2026-08-08 (KST) · **상태**: 설계 검토 — 미결정 항목은 §11
> **상위 문서**: [`embedded-auth-server-design.md`](embedded-auth-server-design.md)
> **한 줄**: 인증만으로는 페인포인트의 절반만 푼다. 권한 체계도 프로젝트마다 새로 짜고 있다.

---

## 0. 한 장 결론

**문제**: 현재 IX-Auth 설계는 **역할은 있는데 권한이 없다.** `roles.code = "ADMIN"` 뿐이고, ADMIN 이 무엇을 할 수 있는지는 앱이 하드코딩한다. 결국 프로젝트마다 권한 체계를 새로 만든다 — users 테이블보다 반복이 더 많다.

**해법**: 권한을 **성격에 따라 2계층으로 나눈다.**

| 계층 | 대상 | 판정 위치 | 비중 |
|------|------|----------|------|
| **L1 정적 권한** | 역할 · 그룹 · 페이지/메뉴 · 기능 액션 | **앱 로컬** (캐시된 맵으로 판정) | ~90% |
| **L2 인스턴스 권한** | 특정 파일·폴더·문서 하나에 대한 권한 | jar 조회 (캐시 가능) | ~10% |

**Zanzibar 는 참고하되 그대로 하지 않는다.** 임의 관계 그래프 대신 **경로 기반 계층 상속**으로 좁힌다 (§3.2). 이유는 §2.

## 1. 갭 진단 — 지금 무엇이 없는가

| 영역 | 현재 설계 | 갭 | 없으면 앱이 하는 일 |
|------|----------|-----|-------------------|
| 인증 | 로그인·토큰·잠금·세션 | — | — |
| 역할 | `roles` + `user_roles` (평면) | 역할 계층 없음 | 상위 역할 하드코딩 |
| **권한(permission)** | **없음** | 역할이 무엇을 할 수 있는지 정의 자체가 없다 | **역할별 if 문을 앱마다 작성** |
| **그룹** | **없음** | 부서·팀 단위 권한 부여 불가 | 사용자별로 일일이 역할 부여 |
| **페이지/메뉴 권한** | **없음** | — | 라우터마다 역할 체크 하드코딩, 메뉴 노출 로직 중복 |
| **리소스 인스턴스 권한** | **없음** | 파일·폴더·문서 단위 | 자체 ACL 테이블 신설 |
| **액션 구분** | **없음** | read/write/delete/download/share | 없어서 대충 뭉갬 |
| **위임·공유** | **없음** | "A가 B에게 이 문서 공유" | 자체 공유 테이블 |

**가장 큰 구멍은 세 번째다.** 역할만 있고 권한이 없으면 역할은 이름표에 불과하다.

## 2. Zanzibar 를 그대로 못 쓰는 이유

Google Zanzibar 는 훌륭한 모델이지만, 그대로 가져오면 IX-Auth 의 존재 이유가 무너진다.

| Zanzibar 특성 | IX-Auth 에서의 문제 |
|--------------|-------------------|
| 임의 관계 그래프 순회 (`문서의 소유자의 매니저는 볼 수 있다`) | 재귀 조회가 필요 → **매 요청 서버 왕복** → 설계 불변식 2 정면 위반 |
| 전용 분산 스토리지 + Leopard 인덱스 | 별도 인프라 → 불변식 3(앱 DB 공유) 위반 |
| zookie 기반 일관성 토큰 | 앱이 알아야 할 개념이 늘어난다 |
| 오픈소스 구현(SpiceDB·Ory Keto·OpenFGA) | 전부 **독립 서버 제품**. 그럴 거면 IX-Auth 가 아니라 그걸 쓰면 된다 |

> **판단**: Zanzibar 급 표현력이 정말 필요한 시스템이라면 SpiceDB/OpenFGA 를 별도로 도입하는 게 맞다. IX-Auth 는 **업무 시스템 권한의 현실적 90%** 를 관리 포인트 증가 없이 덮는 것이 목표다.

### 그래서 무엇을 포기하는가

| 요구 | 지원 |
|------|------|
| "이 폴더 편집자는 하위 파일도 편집 가능" | ✅ 경로 상속으로 지원 |
| "문서를 특정 사용자/그룹에게 공유" | ✅ 인스턴스 권한으로 지원 |
| "문서 소유자의 **매니저**는 볼 수 있다" | ❌ 관계 그래프 필요 — 미지원 |
| "프로젝트 멤버의 팀의 상위 부서장은…" | ❌ 미지원 |

포기하는 것들은 **조직 관계 모델**을 요구한다. 그건 제품 경계 밖(조직도 = IX-Trust 영역)이라 일관된다.

## 3. 2계층 모델

### 3.1 L1 — 정적 권한 (앱 로컬 판정)

```
users ─┬─ user_roles ──── roles ──┬─ role_permissions ── permissions
       │                          │
       └─ user_groups ─ groups ───┘  (group_roles)
```

**유효 권한** = (직접 부여된 역할 ∪ 소속 그룹의 역할) 의 권한 합집합

- **역할(role)** — 권한 묶음. `ADMIN`, `PM`, `VIEWER`
- **그룹(group)** — 권한 부여 단위. **조직도가 아니다** (§10 경계 참조). `개발팀`, `외부협력사`
- **권한(permission)** — 실제 판정 대상. 코드 체계는 §4

L1 은 사용자당 수십~수백 개 수준이라 **한 번 받아서 캐싱**하면 된다. 매 요청 조회가 필요 없다 → 불변식 2 유지.

### 3.2 L2 — 인스턴스 권한 (조회 필요)

특정 리소스 **하나**에 대한 권한. Zanzibar 관계 튜플의 축소판.

```
resource_grants
  subject_type   user | group | role
  subject_id
  resource_type  file | folder | document | board | ...
  resource_key   경로 또는 ID  (예: /contracts/2026/a.pdf)
  action         read | write | delete | download | share | *
  effect         allow | deny
```

**경로 기반 계층 상속** — 이것이 Zanzibar 그래프를 대체하는 핵심 절충이다.

`/contracts/2026/a.pdf` 에 대한 권한을 물으면 다음을 조회한다:

```
/contracts/2026/a.pdf   ← 정확 매칭
/contracts/2026/        ← 상위 폴더
/contracts/             ← 상위
/                       ← 루트
```

조상 경로 집합을 만들어 `resource_key IN (...)` 으로 한 번에 조회한다. **재귀 그래프 순회가 없다.**

> ⚠️ **prefix LIKE 가 아니다** (2026-08-08 구현 시 정정). `/contracts/2026/a.pdf` 판정에 필요한 것은\
> **조상**이지 형제(`/contracts/2026/b.pdf`)가 아닌데, prefix 는 형제까지 잡아 권한이 샌다.\
> 조상 목록은 앱 서버에서 계산하므로 DB 는 단순 IN 조회만 한다.

**판정 규칙**:
1. `deny` 가 하나라도 있으면 거부 (명시적 거부 우선)
2. 없으면 `allow` 가 하나라도 있으면 허용
3. 둘 다 없으면 L1 권한으로 폴백 (예: `file:*:download` 를 가진 역할)
4. 그것도 없으면 거부 (기본 거부)

## 4. 권한 코드 체계

```
<domain>:<resource>:<action>
```

| 예시 | 의미 |
|------|------|
| `page:admin.users:view` | 사용자 관리 페이지 접근 |
| `page:settings:*` | 설정 페이지의 모든 액션 |
| `board:notice:write` | 공지 게시판 쓰기 |
| `file:contracts/**:download` | 계약 폴더 이하 다운로드 |
| `*:*:*` | 전권 (슈퍼 관리자) |

- 와일드카드 `*` (한 세그먼트) 와 `**` (하위 전체) 지원
- `domain` 은 앱이 자유롭게 정의한다. IX-Auth 는 문자열로만 다룬다
- **페이지/메뉴 권한이 1급 시민이다** — 별도 테이블이 아니라 `page:` 도메인으로 표현. 카테고리는 점 표기(`page:admin.users`)로 계층 표현

### 왜 별도 페이지 테이블을 만들지 않는가

페이지·메뉴 구조는 앱마다 완전히 다르다. IX-Auth 가 페이지 테이블을 가지면 앱의 라우팅 구조를 알아야 하고, 그러면 앱마다 스키마가 달라진다. **문자열 권한 코드로 두면 앱이 자기 구조를 그대로 표현할 수 있다.**

메뉴 노출용으로는 "내 권한 목록" API 하나면 충분하다 (§6).

## 5. 캐싱 전략 — 불변식 2를 지키는 방법

**문제**: 권한을 토큰에 전부 담으면 토큰이 비대해진다. 매 요청 조회하면 불변식 2 위반.

**해법**: 세 조각으로 나눈다.

| 무엇 | 어디에 | 갱신 |
|------|--------|------|
| 사용자의 **역할·그룹 코드** | **JWT 클레임** (`ixauth_roles`, `ixauth_groups`) | 토큰 재발급 시 |
| **역할 → 권한 맵** | 앱 메모리 캐시 (JWKS 와 같은 패턴) | `permissions_version` 변경 감지 시 |
| **인스턴스 권한(L2)** | jar 조회 + 짧은 TTL 캐시 | 리소스 접근 시 |

```
앱 부팅 → GET /authz/permission-map  (역할→권한 전체 맵, 보통 수 KB)
요청마다 → 토큰의 역할 + 캐시된 맵으로 로컬 판정        ← 네트워크 0
파일 접근 → POST /authz/check                         ← 이때만 조회
```

**`permissions_version`**: 권한 맵이 바뀌면 정수 버전이 올라간다. jar 응답 헤더(또는 토큰 클레임)에 실어 보내고, 앱은 버전이 다르면 맵을 다시 받는다. 폴링이 필요 없다.

> **불변식 2 재정의 필요** — 현행 문구는 "매 요청 토큰 검증에 jar 를 호출하지 않는다" 이다. L2 조회는 **토큰 검증이 아니라 리소스 접근 판정**이므로 위반이 아니지만, 오해를 막기 위해 불변식 문서에 예외를 명시한다 (§10).

## 6. API (초안)

### 판정

| 메서드 | 경로 | 용도 |
|--------|------|------|
| POST | `/authz/check` | 단건 판정 — `{subject, resourceType, resourceKey, action}` → `{allowed, reason}` |
| POST | `/authz/batch-check` | 여러 건 한 번에 (목록 화면에서 N+1 방지) |
| GET | `/authz/permission-map` | **역할 → 권한 전체 맵** (앱이 캐싱, `permissions_version` 동반) |
| GET | `/authz/my-permissions` | 현재 사용자의 유효 권한 목록 (메뉴 노출용) |
| GET | `/authz/list-resources?action=read&type=file` | 사용자가 접근 가능한 리소스 키 목록 (목록 조회 필터용) |

`list-resources` 는 Zanzibar 의 reverse index 에 해당한다. 경로 기반이라 prefix 인덱스로 구현 가능하다.

### 관리

| 메서드 | 경로 | 용도 |
|--------|------|------|
| GET/POST/DELETE | `/admin/permissions` | 권한 코드 정의 |
| GET/POST/PATCH/DELETE | `/admin/roles/{id}/permissions` | 역할에 권한 부여 |
| GET/POST/DELETE | `/admin/groups` · `/admin/groups/{id}/members` · `/{id}/roles` | 그룹 관리 |
| GET/POST/DELETE | `/admin/resource-grants` | 인스턴스 권한 부여/회수 |

## 7. 스키마 추가 — 6종

기존 7종 + 인가 6종 = **13종**.

| 테이블 | 핵심 컬럼 | 계층 |
|--------|-----------|------|
| `permissions` | id, code(uniq), domain, resource, action, description | L1 |
| `role_permissions` | role_id, permission_id | L1 |
| `groups` | id, code(uniq), name, description | L1 |
| `user_groups` | user_id, group_id | L1 |
| `group_roles` | group_id, role_id | L1 |
| `resource_grants` | id, subject_type, subject_id, resource_type, resource_key, action, effect, granted_by, expires_at | L2 |

**인덱스 핵심**: `resource_grants (resource_type, resource_key varchar_pattern_ops)` — 경로 prefix 조회용. 이게 L2 성능의 전부다.

**역할 계층**: `roles.parent_id` 로 단순 상속만 지원할지 결정 필요 (§11 Q3).

## 8. 데이터 스코프 (행 단위 필터)는 제외

"자기 부서 데이터만 조회" 같은 요구는 **권한 판정이 아니라 쿼리 필터**다. IX-Auth 가 앱의 쿼리에 개입할 수 없다.

→ IX-Auth 는 **스코프 값만 제공**하고(예: 토큰에 `ixauth_scope: {dept: "DEV"}`), 실제 필터링은 앱이 한다. 이 경계를 흐리면 IX-Auth 가 ORM 영역으로 번진다.

---

## 9. 무엇을 여전히 만들지 않는가

| 항목 | 이유 |
|------|------|
| 관계 그래프 순회 (ReBAC 완전판) | §2 — 필요하면 SpiceDB/OpenFGA |
| 조직도 (부서 트리·직급·보고 라인) | 인사 정보. 그룹은 **권한 단위**이지 조직도가 아니다 |
| ABAC (속성 기반 동적 정책 엔진) | 정책 언어·평가 엔진이 필요. 제품이 통째로 커진다 |
| 워크플로 승인 권한 | 앱 도메인 |
| 행 단위 쿼리 필터 자동 적용 | §8 |

## 10. 기존 규칙에 필요한 조정

이 설계를 채택하면 아래 두 문서를 함께 고쳐야 한다.

### 불변식 2 — 예외 명시

현행: "매 요청 토큰 검증에 jar 를 호출하지 않는다"

추가할 문구:

> **L2 인스턴스 권한 조회(`/authz/check`)는 예외다.** 이는 토큰 검증이 아니라 리소스 접근 판정이며, 파일·문서 접근처럼 빈도가 낮은 경로에서만 발생한다. 다만 ① 짧은 TTL 캐시를 권장하고 ② **jar 장애 시 L1 권한으로 폴백(fail-safe)** 하거나 명시적으로 거부(fail-secure)할지를 앱이 설정할 수 있어야 한다.

### 제품 경계 — 그룹 재분류

현행 제외 목록에 "조직(Organization)·부서·직급 트리" 가 있다. **그룹은 여기서 분리한다.**

| | 성격 | IX-Auth |
|---|------|---------|
| **권한 그룹** | 권한을 묶어 부여하는 단위. 평면 구조 | ✅ 포함 |
| **조직도** | 부서 트리·직급·보고 라인. 인사 정보 | ❌ 제외 (IX-Trust) |

구분 기준: **"이 그룹에 권한을 주는가"** 면 IX-Auth, **"이 사람이 조직 어디에 속하는가"** 면 앱 또는 IX-Trust.

## 11. 결정이 필요한 사항

| # | 질문 | 선택지 | 권고 |
|---|------|--------|------|
| A1 | L2(인스턴스 권한)를 **P1 에 포함**할까 | (a) P1 포함 (b) **P1 은 L1 만, L2 는 P2** | **(b)** — L1 만으로 페이지·기능 권한이 덮인다. L2 는 스키마만 P0 에서 확정해 두고 구현은 뒤로 |
| A2 | 역할 계층(상속) | (a) 지원 (b) **미지원, 권한 중복 부여** | **(b)** — 계층은 편해 보이지만 "왜 이 권한이 있지" 추적이 어려워진다. 필요하면 나중에 추가가 쉽다 |
| A3 | `deny` 규칙 | (a) **지원** (b) allow 만 | **(a)** — "전체 허용 + 특정 폴더 제외" 가 실무에서 자주 나온다 |
| A4 | 권한 코드 자유 정의 vs 사전 등록 | (a) 앱이 임의 문자열 (b) **`permissions` 테이블에 등록된 것만** | **(b)** — 관리 화면에서 목록을 보여주려면 등록이 필요하다. 오타 방지도 됨 |
| A5 | 시간 제한 권한(`expires_at`) | (a) **지원** (b) 미지원 | **(a)** — 임시 접근 권한이 실무에 흔하고, 컬럼 하나 값이다 |

## 12. 구현 순서 제안

```
P0 (계약)   인가 스키마 6종 + 권한 코드 체계 + /authz API 계약 확정
            → 인증 계약과 함께 확정해야 한다. 나중에 붙이면 roles/users 를 다시 건드린다

P1 (MVP)    인증 + L1 인가 함께 구현
            · permissions / role_permissions / groups / user_groups / group_roles
            · GET /authz/permission-map · /my-permissions
            · 관리 화면에 권한·그룹 탭
            · SDK 에 로컬 판정 헬퍼 (hasPermission)

P2          L2 인스턴스 권한
            · resource_grants + 경로 prefix 인덱스
            · POST /authz/check · batch-check · list-resources
            · 폴더 상속 · deny 우선 · 만료

P3          실제 프로젝트 적용 검증
```

**인가만 따로 먼저 구현할 수는 없다** — `users`/`roles` 위에 얹히는 구조라 인증 구현이 선행돼야 한다. 다만 **계약(P0)은 지금 함께 확정해야 한다.** 나중에 붙이면 스키마를 다시 설계하게 된다.

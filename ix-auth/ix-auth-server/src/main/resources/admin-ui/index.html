IX-Auth 관리

사용자 추가

비밀번호를 비우면 초대 방식이다 — 계정은 PENDING 으로 만들어지고, 본인이 메일 링크로 직접 정한다. 관리자가 정한 비밀번호를 따로 알려 주는 경로(메신저·구두)가 대개 가장 약한 고리다.

일괄 등록 (CSV)
email,name,roles 세 칸. 첫 줄이 머리글이면 건너뛴다. 역할이 여럿이면 "ADMIN,USER" 처럼 따옴표로 감싸거나 ADMIN;USER 로 적는다.
비밀번호는 만들지 않는다. 수백 명에게 비밀번호를 안전하게 전달할 경로가 없어서다 — 계정은 PENDING 으로 만들어지고 초대 링크로 본인이 정한다. 한 줄이 틀려도 나머지는 들어간다.
사용자 속성 정의
attributes(JSONB) 에 무엇이 들어와야 하는지 정한다. 정의가 없으면 아무 검사도 하지 않는다 — 지금까지 쓰던 앱이 그대로 동작한다. 정의를 두면 앱마다 dept·department·deptCode 가 섞이는 일을 막을 수 있다.

정의를 지워도 사용자에게 저장된 값은 그대로 남는다. 정의를 잘못 지운 실수가 곧 데이터 손실이 되면 안 되기 때문이다. 정의에 없는 키를 거부하려면 설정 탭의 account.strict-attributes 를 켠다 — 켜기 전에 쓰이는 키를 모두 등록해야 한다.

역할 추가
권한 등록
사전 등록제 — 등록된 코드만 역할에 부여할 수 있다. 형식 domain:resource:action
그룹 추가
권한을 묶어 부여하는 단위다. 조직도가 아니다.
파일·폴더 권한 (L2)
역할 권한(L1)과 다르다. 여기는 리소스 하나에 거는 권한이고, 앱은 IX-Auth 에 물어서 판정한다. / 로 끝나면 폴더로 보고 하위로 상속된다.

DENY 가 ALLOW 를 이긴다. /contracts/ 에 ALLOW 를 주고 /contracts/secret/ 에 DENY 를 주면, 그 하위만 막힌다 — "전체 허용 + 일부 제외" 가 실무에 가장 흔하다.

판정 시험
실제 앱이 묻는 것과 같은 질문을 던져 본다. 근거(reason)까지 돌려준다.
리소스 종류
파일이 어디에 있느냐에 따라 키 표기가 다르다. 표기가 어긋나면 권한이 조용히 없는 것이 된다 — /contracts/a.pdf 로 주고 contracts/a.pdf 로 물으면 걸리지 않는데, 그 결과는 "권한 없음" 과 구분되지 않는다. 그래서 종류마다 정규화 규칙을 정해 둔다.

저장소가 판정을 고르면 IX-Auth 는 그 종류를 판정하지 않고 DELEGATED 라고 답한다. 파일서버(Nextcloud·MinIO 등)가 자체 권한을 가진 경우, 두 곳에서 각각 판정하면 어느 쪽이 진짜인지 알 수 없게 된다.

약관
먼저 설정 탭에서 terms.enabled 를 켜야 사용자에게 보인다. 꺼져 있으면 여기서 등록·게시는 되지만 가입 화면과 로그인 응답에는 아무것도 나가지 않는다.
약관은 버전을 갖는다. 개정할 때 기존 것을 고치지 않고 새 버전을 낸다 — 고치면 이미 동의한 사람의 이력이 가리키는 내용이 달라져 증빙이 아니게 된다. 그래서 게시된 약관은 내용을 수정할 수 없다.

표준 약관 불러오기는 이용약관 · 개인정보 수집·이용 · 만 14세 이상 · 광고성 정보 수신 네 건을 초안으로 넣는다. 이미 있는 코드는 건너뛰므로 여러 번 눌러도 안전하다. 문안은 고쳐 쓰라고 주는 예시다 — [ ] 로 비워 둔 자리를 채우고 게시하라.

새 약관 · 새 버전
이미 있는 코드를 넣으면 그 약관의 다음 버전이 된다. 버전 번호는 서버가 매긴다. 만들면 초안이라 사용자에게 보이지 않는다 — 게시 버튼을 눌러야 나간다.
동의 이력
지우거나 고칠 수 없다. 철회는 덮어쓰기가 아니라 거절 기록이 한 줄 더 쌓이는 것이다 — "언제부터 언제까지 동의 상태였는가" 가 곧 증빙이다. 위 표의 이력 버튼으로 버전별로 본다.
설정
바꾸면 즉시 반영된다 (재시작 불필요). 누가 무엇을 바꿨는지는 감사 로그에 남는다. 키·비밀번호 같은 시크릿은 여기서 다루지 않는다 — 화면에서 편집 가능하게 만들면 유출면이 넓어진다.
가입 승인 대기
설정 탭에서 가입 방식을 승인제 로 두었을 때만 여기에 쌓인다. 승인하면 바로 로그인할 수 있고, 거절하면 비활성 상태로 남는다 — 지우지 않는 이유는 같은 주소로 반복 시도하는 것을 막기 위해서다.
설정 상태
메일이 잘못 설정돼 있으면 "비밀번호 찾기를 눌렀는데 안 온다" 로만 드러나고 원인은 부팅 로그에만 남는다. 여기서 바로 확인한다.
발급된 메일 링크
누구에게 · 무슨 용도로 · 언제 나갔고 · 아직 유효한지. 토큰 값은 보이지 않는다 — 관리자가 남의 재설정 링크를 볼 수 있으면 그것이 곧 계정 탈취 경로다.
계정이 만들어지는 세 가지 경로
경로언제 쓰나기본값
초대 관리자가 만들고 본인이 비밀번호를 정한다. 사용자 추가 시 비밀번호를 비우면 이 방식이다 — 계정은 PENDING 이고, 링크를 열어야 ACTIVE 가 된다 항상 가능
회원가입 본인이 직접 가입한다. 앱이 가입 화면을 만들고 POST /auth/signup 으로 중계한다 꺼져 있음
소셜 로그인 Microsoft·카카오·네이버로 처음 들어온 사용자를 자동 생성 꺼져 있음

회원가입이 기본으로 꺼져 있는 이유 — 설치형 제품이라 사내용으로 띄운 인스턴스가 대부분이다. 열어 두면 주소를 아는 누구나 계정을 만들 수 있다. 외부 사용자를 받는 서비스라면 켜면 된다.

설정설명
ixauth.account.signup-enabled true 로 바꾸면 회원가입이 열린다
ixauth.account.signup-allowed-domains 가입 허용 도메인 제한 (예: prost.kr). 비우면 제한 없음 — 사내 서비스를 열 때 이것만으로 상당 부분 걸러진다
ixauth.account.require-email-verification 인증을 마쳐야 로그인. 가입을 열었다면 함께 켜는 것을 권한다 — 남의 주소로 가입하는 것을 막는다
ixauth.social.auto-signup 소셜로 처음 들어온 사용자를 자동 생성

가입 요청은 이미 가입된 주소여도 성공으로 답한다 — 다르게 답하면 그 화면이 가입자 명부를 조회하는 도구가 된다. 대신 그 주소의 주인에게만 "이미 계정이 있다" 는 메일이 간다. 현재 설정은 시스템 탭에서 확인한다.

소셜 로그인 (Microsoft · 카카오 · 네이버 · Google)

콜백은 앱이 받는다. IX-Auth 는 외부에 노출되지 않으므로 provider 가 브라우저를 이쪽으로 돌려보낼 수 없다. provider 콘솔에 등록할 Redirect URI 는 전부 앱 주소다.

provider이메일 검증 신호기존 계정 자동 연결
카카오is_email_verified 를 준다가능
Microsoft주지 않는다 — 테넌트를 조직 ID 로 고정한 경우에만 신뢰테넌트 고정 시 가능
네이버주지 않는다불가 — 본인이 직접 연결
Googleemail_verified — OIDC 표준 클레임가능

이메일만 보고 기존 계정에 붙이면, 남의 주소를 자기 소셜 계정에 적어 넣는 것만으로 그 계정을 가져갈 수 있다. 그래서 provider 가 "검증했다" 고 명시한 경우에만 붙인다. 매칭 기준도 이메일이 아니라 provider 의 불변 식별자다 — 이메일은 바뀌고, 바뀐 주소가 남에게 재할당될 수도 있다.

Microsoft 테넌트를 common 으로 두면 아무 Microsoft 계정이나 동의 화면을 통과한다. 사내 시스템이라면 조직 테넌트 ID 를 넣는다.

비밀번호 찾기가 동작하려면

메일 설정 두 가지가 필요하다. 하나라도 비면 링크가 사용자에게 닿지 않는다.

설정설명
ixauth.mail.transport SMTP(권장) · WEBHOOK(사내 메일·폐쇄망) · LOG(개발용 — 링크를 로그에만 남긴다)
ixauth.mail.app-base-url 앱 주소다. IX-Auth 주소가 아니다 — IX-Auth 는 외부에 노출되지 않으므로 사용자의 브라우저가 열 수 없다

앱은 /reset-password 같은 화면을 두고, 사용자가 입력한 새 비밀번호를 토큰과 함께 IX-Auth 로 중계한다.

재설정 요청은 계정이 없어도 성공으로 답한다. 다르게 답하면 그 화면이 가입자 명부를 조회하는 도구가 된다. 링크는 1회용이고, 새로 발급하면 옛 링크는 무효가 된다. 재설정에 성공하면 그 계정의 모든 세션이 끊긴다 — 재설정하는 이유는 대개 계정을 빼앗겼기 때문인데, 세션을 남기면 빼앗은 쪽이 그대로 남기 때문이다.

2단계 인증 (TOTP)

설정 탭의 mfa.mode 로 정한다. 사용자는 인증 앱(Google Authenticator 등)에 등록하고, 로그인 때 6자리 코드를 한 번 더 넣는다.

모드동작
OPTIONAL사용자가 원하면 켠다 (기본)
REQUIRED_ADMIN관리 권한자에게 요구
REQUIRED_ALL전원에게 요구

⚠ 필수로 바꿔도 아직 등록하지 않은 사람의 로그인을 막지 않는다. 막으면 켜는 순간 전원이 못 들어온다. 대신 로그인 응답에 mfaSetupRequired 를 실어 보내므로, 등록을 강제하는 것은 앱의 몫이다.

백업 코드는 등록할 때 한 번만 보인다. 휴대폰을 잃으면 그것이 유일한 복구 수단이다. 그마저 잃은 사용자는 사용자 목록의 MFA 초기화 로 풀어 준다 — 그 조작은 감사 로그에 남고 본인에게 알림 메일이 간다. 관리자가 조용히 남의 2단계를 끄는 일이 없어야 하기 때문이다.

소셜 로그인은 2단계를 요구하지 않는다 — provider 가 본인확인을 마친 경로로 보기 때문이다. REQUIRED_ALL 에서는 그것이 우회로가 된다는 뜻이므로, 엄격히 막아야 한다면 소셜 로그인을 끈다.

약관 동의

약관 탭에서 등록하고 게시 해야 효력이 생긴다. 초안 상태로는 아무에게도 보이지 않는다. 각 행의 본문 으로 그 버전에 담긴 문구를 그대로 확인할 수 있다 — "v2 에 동의함" 이라는 이력은 v2 의 문구를 읽을 수 있어야 증빙이 된다.

처음이라면 표준 약관 불러오기 로 시작한다. 이용약관 · 개인정보 수집·이용 · 만 14세 이상 · 광고성 정보 수신 네 건이 초안으로 들어온다. 이미 있는 코드는 건너뛰므로 여러 번 눌러도 안전하다. 법률 자문이 아니라 고쳐 쓸 출발점이다 — 회사명·보유 기간처럼 서비스마다 다른 자리는 [ ] 로 비워 두었고, 그대로 게시하면 사용자 눈에 대괄호가 그대로 보인다.

필수 약관을 새 버전으로 게시하면 재동의를 요구한다. 이때도 로그인은 막지 않고 응답에 termsAgreementRequired 를 실어 준다 — 2단계 인증과 같은 이유다. 동의 화면으로 보내는 것은 앱이 한다.

동의 이력은 지우지 않는다. 언제·어느 버전에·어느 IP 에서 동의했는지가 법적 증빙이기 때문이다. 그래서 이미 동의한 사람이 있는 약관은 삭제되지 않는다(오타가 난 초안은 동의 전이라 지울 수 있다).

소셜 로그인에도 약관 동의를 요구한다. 2단계 인증과 다르게 다루는 이유는, 약관은 우리와 사용자 사이의 합의라 provider 가 대신 받아 줄 수 없기 때문이다.

계정을 지키는 스위치들

전부 설정 탭에 있다. 기본값은 "지금까지와 같은 동작" 이라, 켜야 달라진다.

설정켜면 무엇이 달라지나
account.notify-new-device 모르는 기기·IP 에서 로그인하면 본인에게 메일. 계정 탈취를 사용자가 스스로 알아채는 거의 유일한 통로다 (기본 켜짐)
account.max-concurrent-sessions 계정당 동시 로그인 수 제한. 초과하면 가장 오래된 것부터 끊는다. 0 이면 무제한(기본) — 걸어 두면 여러 기기를 쓰는 사람이 영문 모르고 로그아웃되어 장애로 느낀다
account.self-delete-mode 본인 탈퇴 허용 여부. 유예 모드면 그 기간 안에 로그인 한 번으로 취소된다. 계정은 지우지 않고 비활성으로 남는다
password.check-breached 이미 유출된 비밀번호를 거부한다. 비밀번호가 외부로 나가지는 않는다 (해시 앞부분만 조회). 폐쇄망에서는 쓸 수 없다
password.history-count 최근 N개 재사용 금지. 0 이어도 직전 것은 늘 막힌다
captcha.enabled 가입·비밀번호 찾기에 CAPTCHA. 앱이 먼저 토큰을 보내도록 고쳐야 한다 — 그 전에 켜면 해당 화면이 막힌다
mfa.step-up-actions 비밀번호 변경·탈퇴 같은 민감 작업에 2단계 코드를 한 번 더 요구
메일이 안 갈 때 어디를 보나

메일 탭에 발송 이력이 있다. 받는 사람·용도·상태가 남으므로 "보냈는데 못 받았다" 를 여기서 먼저 가린다.

상태뜻
SENT통로에 넘겼다 (상대 메일함 도착까지 보장하지는 않는다)
FAILED넘기지 못했다. 재시도 버튼으로 다시 보낸다
SKIPPED보내지 않았다. 전송 방식이 LOG 일 때 — 사용자는 아무것도 받지 못한다

본문과 링크는 저장하지 않는다. 재설정 링크가 이력에 남으면 그 이력을 본 사람이 남의 계정을 가져갈 수 있기 때문이다. 같은 이유로, 서버를 다시 시작하면 재시도할 원본이 사라져 재시도 가 거절된다 — 그때는 사용자에게 다시 요청하게 하는 편이 맞다.

문구를 바꾸려면 같은 탭의 템플릿을 쓴다. 한국어·영어를 따로 두고, 비워 두면 기본 문구가 나간다. 저장 전에 미리보기 로 자리표시자가 제대로 채워지는지 본다.

사용자를 한꺼번에 등록하려면

사용자 탭의 일괄 등록에 CSV 를 붙여넣는다 (email,name 형식). 비밀번호 없이 만들어지고 초대 메일이 나가므로, 받는 사람이 직접 비밀번호를 정한다.

한 줄이 잘못돼도 나머지는 들어간다. 결과 표에 줄 번호와 실패 사유가 나오므로 그 줄만 고쳐 다시 올리면 된다.

부서·사번 같은 값을 함께 넣으려면 속성 정의를 먼저 등록한다. 정의해 두면 형식이 검증되고, 앱마다 제각각인 키가 생기는 것을 막는다.

권한은 두 층으로 나뉜다
층대상판정 위치
L1 역할 · 그룹 · 페이지 · 기능 앱이 스스로 판정한다. IX-Auth 를 호출하지 않는다 — 앱이 permission-map 을 받아 캐싱하기 때문
L2 파일 · 폴더 · 문서 하나 IX-Auth 에 물어본다 (/authz/check). 파일 접근처럼 빈도가 낮은 경로에만

이 화면의 역할·권한 탭은 L1 이다. 파일·폴더 권한(L2)은 API 로 부여한다 (/admin/resource-grants).

Zanzibar 와 무엇이 다른가

자주 오해받는 부분이라 짚어 둔다. L1 은 Zanzibar 가 아니다 — 역할에 권한 코드를 붙이는 고전적인 RBAC 이다. 동적으로 추가·관리되는 건 맞지만, Zanzibar 의 특징인 관계 기반 판정(ReBAC)은 쓰지 않는다.

L2 가 Zanzibar 를 축소 참고한 쪽이다. 다만 임의 관계 그래프 대신 경로 상속만 지원한다. 그래서 이런 차이가 난다:

요구지원
이 폴더 권한을 하위 파일도 갖는다가능
문서를 특정 사용자·그룹에게 공유가능
“문서 소유자의 매니저는 볼 수 있다”불가

마지막 것은 조직 관계 모델이 필요한데, 그건 IX-Auth 의 범위 밖이다 (여러 앱이 신원을 공유하는 영역 = IX-Trust). 그런 표현력이 정말 필요하면 SpiceDB·OpenFGA 같은 전용 제품을 쓰는 편이 맞다.

권한 코드 문법

<domain>:<resource>:<action> — 세 부분을 콜론으로 나눈다. domain 은 앱이 자유롭게 정한다(page, board, file …). 계층은 . 이나 / 로 표현한다.

패턴요청결과
page:*:viewpage:admin.users:view허용
page:admin.*:viewpage:admin.users:view허용
page:admin.*:viewpage:admin.users.detail:view거부 — * 는 한 단계만
page:admin.**:viewpage:admin.users.detail:view허용 — ** 는 이하 전부
file:contracts/**:downloadfile:contracts/2026/a.pdf:download허용
*:*:*무엇이든허용 (전권)

** 는 마지막 단계에만 올 수 있다. a.**.c 같은 패턴은 등록 시 거부된다.

권한을 바꿨는데 화면이 그대로라면

정상이다. 앱은 권한 맵을 캐싱하고, 토큰이 새로 발급될 때 변경을 알아챈다. 그래서 최대 액세스 토큰 수명(기본 15분) 만큼 반영이 늦을 수 있다.

즉시 반영해야 하면 사용자 탭에서 해당 사용자의 세션을 종료한다. 다시 로그인하면서 새 권한이 실린다.

역할 · 그룹을 언제 쓰나
개념쓰임
역할권한 묶음. PM, VIEWER 처럼 “무엇을 할 수 있는가”
그룹사람 묶음에 역할을 한 번에 부여. 개발팀, 외부협력사

그룹은 조직도가 아니다. “이 그룹에 권한을 주는가” 면 여기에 두고, “이 사람이 조직 어디에 속하는가” 는 앱이 관리한다.

역할에는 계층(상속)이 없다. 상위 역할을 만드는 대신 권한을 중복 부여한다 — “왜 이 권한이 있지” 를 추적할 수 있게 하려는 의도다.

내려받는 파일에는 이메일·IP·User-Agent 가 그대로 들어 있다. 그래서 내보낸 사실 자체가 감사 로그에 남는다(AUDIT_EXPORTED). 한 번에 받을 수 있는 행 수에는 상한이 있고(설정 audit.export-max), 걸리면 파일 마지막 줄에 잘렸다고 적힌다.

IP 가 앱 서버 주소로만 찍힌다면 — IX-Auth 는 앱 뒤에 있어서, 앱이 최종 사용자 IP 를 넘겨주지 않으면 앱 서버 주소만 남는다. 앱에서 로그인을 중계할 때 ip 를 함께 보내거나, 리버스 프록시가 X-Forwarded-For 를 전달하도록 설정한다. (Express 라면 app.set('trust proxy', true))

발송 이력
본문과 링크는 저장하지 않는다. 재설정 링크가 DB 에 남으면 그것이 곧 계정 탈취 경로다 — 여기 남는 것은 누구에게 · 무슨 용도로 · 어떻게 됐는지 뿐이다.
SKIPPED 는 실패가 아니라 전송 방식이 '발송 안 함' 이어서 나가지 않은 것이다. GAVE_UP 이 운영자가 손대야 하는 것이고, FAILED 는 아직 재시도가 남아 있다.
메일 템플릿
고치지 않으면 코드의 기본 템플릿이 쓰인다 — 이 화면이 생겼다고 이미 나가던 메일 문구가 달라지지 않는다. 초기화는 고친 것을 지워 기본값으로 되돌린다.
자리표시자 {name} · {link} · {productName} · {expiresIn}. 새 기기 알림은 {at} · {ip} · {device}, 초대는 {inviter} 를 더 쓴다. 모르는 이름은 그대로 남는다 — 오타를 눈으로 잡을 수 있게 한 것이다.

언어는 사용자 속성 locale(ko·en)이 정하고, 없으면 설정 mail.default-locale 을 쓴다. 그 언어의 템플릿이 없으면 기본 언어로 내려간다 — 메일이 안 나가는 것보다 다른 언어로라도 나가는 편이 낫다.

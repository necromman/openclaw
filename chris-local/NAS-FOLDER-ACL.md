# NAS 폴더 접근권한 설계 (관리 화면에서 폴더마다 권한 지정)

> 관리 화면에 NAS 폴더 트리를 띄우고, 폴더마다 역할·부서·개인별로 **숨김 / 읽기 / 쓰기** 를 지정하는 기능의 설계 정본이다.\
> 작성 2026-09-09 (KST). **같은 날 0단계(NAS 그룹·마운트)와 1단계(규칙 표·판정·트리 API·관리 화면)를 구현했다.**
> 무엇이 실제로 들어갔고 설계와 어디가 달라졌는지는 12절에 있다.
>
> 관련 정본: [AUTH-DEPARTMENTS.md](AUTH-DEPARTMENTS.md) 13절(폴더 경계 = 에이전트 워크스페이스),

## 1. 결론 5줄

1. **만들 것은 "경로 규칙 표 1개 + 판정 모듈 1개 + 폴더 트리 화면 1개" 다.** 부서 경계(에이전트 단위)는 그대로 두고, 그 아래에 **폴더 단위 평면**을 새로 하나 얹는다. 기존 부서 게이트를 고치지 않는다.
2. **규모는 중간이다.** 3단계로 나누면 1단계가 신규 10파일 + 수정 5파일, 약 1,000줄. 전체(쓰기 포함)는 신규 18파일 안팎, 약 2,300줄.
3. **개인 규칙은 1단계에 들어간다.** 설계 초안은 2단계로 미뤘으나 사용자가 "사용자별로 지정할 수 있어야 한다" 고 확정해(2026-09-09) 앞당겼다. 역할·부서·개인 세 종류 전부가 1단계에 있다.
4. **1단계는 사람이 화면에서 폴더를 훑는 경로만 막는다.** 도구 실행 컨텍스트[<sup>1</sup>](#g1)에 사람 신원이 없다는 것이 실측으로 확인됐고(3.4), 에이전트 파일 읽기까지 넓히는 것은 성격이 다른 작업이라 3단계로 뺀다.
5. **1단계는 읽기·숨김만 한다.** 지금 마운트는 읽기 전용이고, 쓰기를 열면 NAS 쪽 방어선이 통째로 사라지는 것이 실측으로 확인됐다(4.3). 쓰기는 3단계다.
6. **선행 조건은 2026-09-09 에 풀었다.** 게이트웨이[<sup>2</sup>](#g2) 컨테이너의 사용자(uid 1000)가 **실제 공유를 한 글자도 못 읽던 것**(4.2 실측)을 NAS 전용 그룹 신설과 `group_add` 로 해결했다. 결과는 12.1.

### 2.3 폴더 이름 실태 (경로 정규화 규칙의 근거)

| 항목                        | 실측                                                                       | 설계에 주는 요구                                                   |
| --------------------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| 한글 폴더명                 | 거의 전부. 공유 이름 자체가 한글                                           | 규칙 키를 바이트가 아니라 유니코드 문자열로 다뤄야 한다            |
| 자모 분리(NFD) 이름         | **10건 존재**. 예: `#광고관리/1. sns 이미지_브랜딩광고/` 아래 이미지 파일들 | **NFC 정규화 후 비교**. 안 하면 같은 폴더가 두 개로 보인다        |

| 심볼릭 링크                 | **0건** (공유 00~06, `디자인PC` 전부)                                      | 그래도 realpath 후 루트 봉쇄를 유지한다                            |

**모든 공유에 `#recycle` 이 있고**(휴지통), `@eaDir`(Synology 인덱스), `@tmp` 계열이 섞인다. 이 셋은 트리에서 기본 제외한다.

**개인 공유 6개 전부에 `보안폴더` 가 있다**(`01_이화정/보안폴더`, `03_장혜린/00_보안폴더`, `06_박정현/12. 보안폴더` 등).\
사용자가 "숨김" 을 가장 먼저 걸 곳이 여기다. 기본 자세를 **숨김**으로 잡아야 하는 실증이다.

**도구 실행 컨텍스트에 사람 신원이 없다.** `packages/agent-core/src/tool-execution-context.ts:6-9` 의 필드는 `assistantMessage`·`toolCall` 둘뿐이고, 진단 이벤트(`src/infra/diagnostic-events.ts:529-549`)에도 `profileId` 가 없다. 그래서 **도구 계층은 "누가 부르는지" 를 모른다.**

감사 원장이 사람을 붙이는 우회로(`src/audit/user-activity-session-actors.ts:20`, 세션키 -> 사람 인메모리 512개 LRU)를 **인가에 쓰면 안 된다.** 재시작하면 비고, 비면 판정이 열리는 방향으로 실패한다. 감사 모듈 자신이 "세션 키로 사람을 역산하지 않는다" 를 규칙으로 적어 두었다.

**대신 쓸 수 있는 길**: 세션에는 생성자가 이미 남아 있다(`src/config/sessions/session-entry-provenance.ts`, 부서 판정이 `isSessionCreatorProfile` 로 쓰고 있다). 그래서 **런을 준비하는 시점에** 그 사람의 폴더 규칙을 펼쳐 "허용 루트 목록 + 거부 서브트리 목록" 으로 만들고, 그것을 `fsPolicy` 에 실어 도구를 조립한다. 도구는 여전히 사람을 모르지만, **그 런의 도구가 애초에 잘못된 루트를 갖지 못하게** 된다. `assertSandboxPathWithinAnyRoot` 가 이미 여러 루트를 받으므로 허용 쪽은 그대로 쓰고, 거부 서브트리 검사만 새로 넣는다.

이것이 타당성 문서의 "경로 B" 를 전부 하지 않고 필요한 만큼만 하는 방법이고, 그래도 3단계 규모다.

### 3.5 첨부와 채팅 검색

- **첨부는 이 기능의 대상이 아니다.** 채팅 첨부는 미디어 저장소에 살고 NAS 에 없다. 판정은 이미 `src/gateway/inbound-media-access.ts:129` 가 한다. 다만 `media_read` 가 워크스페이스 경로를 가리키면 3.4 의 가드를 지나므로, 3단계에서 같이 닫힌다.
- **채팅 검색 결과**는 메모리 색인을 통해 나온다. 1·2단계에서는 **사이드카를 만들지 않는 것**으로 막는다(3.3). 색인 시점 제외이므로 질의 시점에 새 규칙이 바로 반영되지는 않고, 다음 동기까지 늦는다(최대 30분).

### 3.6 감사

| 무엇                | 파일:줄                                                            |
| ------------------- | ------------------------------------------------------------------ |
| 종류 정본           | `packages/gateway-protocol/src/schema/audit-user-activity.ts:17-27` (`access_denied` 이미 있다) |
| 거부 기록 헬퍼      | `src/gateway/session-view-activity-audit.ts:106` `recordAccessDeniedActivity` (`{reason, surface}`) |
| 관리 행위 기록      | `src/gateway/ix-auth-admin-ledger.ts` `recordIxAuthAdminAction`     |
| 화면 필터 사본      | `ui/src/pages/audit/audit-rows.ts:12` (하드코딩. 새 값은 여기도 넣어야 보인다) |
| 라벨                | `ui/src/i18n/locales/en-ix-auth.ts:140` 부근                        |

**새 kind 를 만들지 않는다.** `access_denied` 에 `surface` 값 두 개(`folder-tree`, `folder-read`)를 더하고, 규칙 변경은 `admin_action` 의 새 `action` 값(`folder_rule_set`·`folder_rule_clear`)으로 남긴다. 종류 목록을 늘리면 화면·CLI·CSV 네 곳을 같이 고쳐야 한다.

### 3.7 거부 코드

읽기 경로의 거부는 **404** 다. 403 으로 답하면 폴더 이름의 존재 여부가 새어 열거가 가능해진다. 부서 경계가 같은 관례를 쓴다(AUTH-DEPARTMENTS 11절).\
이 기능의 요구 자체가 **숨김과 없음을 화면이 구분하지 못하게 하는 것**이므로, 404 는 이 기능에서 반드시 지켜야 하는 값이다.

## 4. NAS 자체 ACL 과의 관계

### 4.1 결론은 그대로다: 두 통제면은 별개다

타당성 문서(`infra/local/openclaw-jinbio-nas-feasibility.md` 1절·8절)의 결론을 2026-09-09 에 다시 확인했고, 바뀐 것이 없다.

- NAS 는 Synology ACL[<sup>5</sup>](#g5)(사용자·그룹별 폴더 권한)로 통제하고, 포크는 앱 계층 논리 경계로 통제한다.
- 신원 서버는 LDAP·AD·POSIX·SCIM 을 설계상 배제한다. **자동 동기화 커넥터가 없다.**
- 즉 이 기능은 NAS ACL 을 **읽지도 쓰지도 않는다.** 사람이 두 면을 각각 관리한다.

실측한 NAS ACL 의 모양(공유 하나의 예):

```text
group:administrators:allow:rwxpdDaARWc--:fd--
group:진바이오테크 NAS 관리자:allow:rwxpdDaARWc--:fd--
group:진바이오테크 직원:allow:rwxpdDaARWc--:fd--
user:<개인 계정>:allow:r-x---a-R-c--:fd--
```

그룹 4개(`administrators`, `진바이오테크 NAS 관리자`, `진바이오테크 직원`, `디자인PC 권한`, `일반`)와 **개인 계정 단위 ACL 이 섞여 있다.** 하위 폴더는 그룹 항목 없이 개인 항목만 갖기도 한다(예: `00_공용폴더/##직원전용`).\
이 구조는 **씨앗으로 한 번 가져오기에는 쓸 만하다**(9절 미결정 5번). 계정 이름이 신원 서버 계정과 자동으로 이어지지는 않는다.

### 4.2 지금 컨테이너는 실제 공유를 읽지 못한다 (선행 조건, 실측)

납품 스택은 **NAS 안에서 돈다**(compose 프로젝트 `openclaw-ixauth`). 그래서 공유는 SMB 를 거치지 않고 **바인드 마운트**[<sup>4</sup>](#g4)로 붙는다. 그런데 게이트웨이 컨테이너의 사용자는 `uid=1000(node)` 이고, NAS 의 로컬 사용자는 uid 1023 부터 시작한다. **uid 1000 은 NAS 에 존재하지 않는 계정이다.**

공유 폴더의 POSIX 모드는 `d---------`(000) 이고 접근은 전부 ACL 이 준다. 그래서 다음이 그대로 나온다.

| 조건                                | 결과              |
| ----------------------------------- | ----------------- |
| uid 1000, 실제 공유 읽기 전용 마운트 | **READ-DENIED**   |
| root(uid 0), 같은 마운트             | READ-OK (18개)    |
| uid 1000 + 보조 그룹 65536(직원 그룹) | **READ-OK (18개)** |
| 같은 조건으로 다른 공유(개인 공유)   | READ-OK (12개)    |
| 같은 조건으로 그룹 항목이 없는 하위 폴더 | **READ-DENIED** |
| 같은 조건, 쓰기 가능 마운트로 파일 생성 | **WRITE-OK**      |

읽어낼 것이 셋이다.

1. **지금 상태로 실제 공유를 붙이면 에이전트가 빈 폴더만 본다.** 이 기능보다 먼저 해결해야 한다.
2. **보조 그룹[<sup>6</sup>](#g6)을 하나 주면 NAS ACL 이 컨테이너에도 그대로 걸린다.** 그룹 항목이 없는 하위 폴더는 컨테이너에서도 안 보인다. 즉 **NAS ACL 이 앱 권한의 상한(최대 도달 범위)으로 작동한다.** 자동 동기화는 아니지만 "앱이 절대 넘을 수 없는 선" 은 생긴다.
3. **그 그룹이 쓰기 권한을 가지면 컨테이너도 곧바로 쓸 수 있다.** 아래 4.3 의 근거다.

권고는 **NAS 에 읽기 전용 전용 그룹을 하나 새로 만들고**(기존 `진바이오테크 직원` 을 재사용하지 않는다) 컨테이너에 `group_add` 로 그 gid 만 주는 것이다. 기존 그룹을 쓰면 그 그룹의 쓰기 권한까지 따라온다.

### 4.3 앱 계층 권한만으로 보장되는 것과 안 되는 것

| 보장된다                                                     | 보장되지 않는다                                                        |
| ------------------------------------------------------------ | ---------------------------------------------------------------------- |
| 브라우저로 들어온 사람이 화면에서 보는 트리·검색·미리보기     | NAS 파일 탐색기(SMB)로 직접 붙는 사람. 거긴 NAS ACL 만 있다             |
| 색인에 들어가는 문서의 범위(사이드카 생성 시점 제외)          | 이미 만들어진 사이드카. 규칙을 바꿔도 다음 동기 전까지 남는다           |
| 3단계 이후: 그 사람의 세션에서 도는 에이전트의 파일 도구 범위 | 게이트웨이 호스트 셸을 가진 사람. 경계 밖이다(AUTH-DEPARTMENTS 7절)     |
| 감사 원장에 남는 거부 기록                                   | 텔레그램 등 계정이 없는 경로. 발신자와 계정을 잇는 장치가 없다(14.3절)  |
| 폴더 이름의 존재 은닉(404)                                   | 사람이 이미 알고 있는 문서를 다른 경로로 받는 것(메일·USB 등)          |

### 4.4 "쓰기" 를 주려면 무엇이 필요한가

지금은 `docker-compose` 가 공유를 `:ro` 로 넣는다(`chris-local/docker-compose.ixauth.yml:197-198`). 쓰기를 열려면 네 가지가 동시에 필요하다.

1. **마운트에서 `:ro` 를 뺀다.** 그 순간 컨테이너 안의 모든 에이전트·모든 세션이 그 폴더에 쓸 수 있게 된다. 폴더별 구분은 마운트가 하지 못한다.
2. **컨테이너의 NAS 신원에 쓰기 권한이 있어야 한다.** 4.2 의 실측에서 직원 그룹으로는 이미 쓰기가 된다. 읽기 전용 그룹을 새로 만들면 쓰기를 여는 시점에 그 그룹의 권한을 따로 올려야 한다.
3. **앱 계층이 유일한 통제가 된다.** OS 가 더는 막지 않으므로, 판정에 구멍이 하나만 있어도 곧바로 원본 훼손이다. 읽기의 구멍은 유출이고 쓰기의 구멍은 **되돌릴 수 없는 손실**이다.
4. **되돌릴 장치가 필요하다.** 공유마다 `#recycle` 이 있지만 그것은 SMB 삭제만 받는다. 컨테이너에서 지운 파일은 거기에 들어가지 않는다. Synology 스냅샷(`@sharesnap` 이 이미 있다) 주기를 확인하고, 쓰기 행위를 전부 감사 원장에 남기는 것이 최소 조건이다.

**SMB 계정 권한은 이 배치에서는 무관하다.** 게이트웨이가 NAS 안에서 돌기 때문에 SMB 를 거치지 않는다. 다른 호스트로 옮기는 날에는 SMB 계정과 마운트 옵션(`file_mode`·`dir_mode`)이 다시 1차 방어선이 된다(DEPLOY 11.4).

## 5. 데이터 모델

### 5.1 표 하나

부서 표(`departments`)·감사 표(`audit_user_activity`)와 같은 자리, 같은 방식이다. **기능 지역 추가 표**라서 정본 스키마 파일에도, 스키마 버전에도 넣지 않는다. 첫 기록 시점에 게으르게 만든다.

```sql
CREATE TABLE IF NOT EXISTS folder_access_rules (
  id TEXT NOT NULL PRIMARY KEY,          -- 규칙 id
  scope_root TEXT NOT NULL,              -- 마운트 루트. 예: "/mnt/nas"
  folder_path TEXT NOT NULL,             -- 루트 기준 상대 경로. "" 는 루트 자신
  subject_kind TEXT NOT NULL,            -- "role" | "department" | "user"
  subject_id TEXT NOT NULL,              -- 역할 코드 / 부서 slug / user_profiles.id
  permission TEXT NOT NULL,              -- "hidden" | "read" | "write"
  inherit INTEGER NOT NULL,              -- 1 = 하위에 상속, 0 = 이 폴더에만
  note TEXT,                             -- 운영자 메모(선택)
  created_by_profile_id TEXT,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
) STRICT;

CREATE UNIQUE INDEX IF NOT EXISTS idx_folder_access_rules_key
  ON folder_access_rules(scope_root, folder_path, subject_kind, subject_id);

CREATE INDEX IF NOT EXISTS idx_folder_access_rules_path
  ON folder_access_rules(scope_root, folder_path);
```

설계 선택과 근거:

| 선택                              | 근거                                                                                          |
| --------------------------------- | --------------------------------------------------------------------------------------------- |
| 경로를 문자열로 키에 쓴다         | 폴더에 안정적인 id 가 없다. inode 는 NAS 마운트를 갈아 끼우면 바뀐다                          |
| `scope_root` 를 따로 둔다         | 마운트 루트가 늘어날 수 있다(`/mnt/nas`, 나중에 다른 저장소). 경로만으로는 어느 루트인지 모른다 |
| `subject_id` 에 부서 slug 를 넣는다 | 접두사를 뗀 값이다(`rnd`). 부서 표와 같은 관례(AUTH-DEPARTMENTS 5절)                          |
| 역할은 게이트웨이 역할 코드       | `superadmin`·`admin`·`executive`·`moderator`·`member`. 신원 서버 역할이 아니라 매핑 뒤의 값     |
| `inherit` 을 규칙마다 둔다        | "이 폴더만" 과 "이 아래 전부" 는 다른 의도다. 하나로 뭉치면 예외를 표현할 수 없다              |
| 외래키를 걸지 않는다              | 부서·프로필 표도 기능 지역이라 생성 순서를 가정할 수 없다(AUTH-DEPARTMENTS 6.2 와 같은 이유)   |
| 사람 삭제 시 규칙을 지우지 않는다 | 감사 대상이다. 주체가 사라진 규칙은 화면에 "고아" 로 표시하고 운영자가 지운다                  |

### 5.2 경로 정규화 규칙

**저장 전에 반드시 통과시킨다.** 순서가 곧 규칙이다.

1. **구분자 통일**: `\` 를 `/` 로 바꾼다. 연속 슬래시를 하나로 줄인다.
2. **루트 기준 상대화**: 절대 경로가 들어오면 `scope_root` 를 떼고 남은 것만 쓴다. 루트 밖이면 거부.
3. **선행·후행 슬래시 제거**: 루트 자신은 빈 문자열 `""` 로 표현한다.
4. **유니코드 NFC 정규화[<sup>7</sup>](#g7)**: 실측에서 NFD 이름이 10건 나왔다(2.3). 안 하면 화면에서 고른 폴더와 저장된 규칙이 다른 것으로 취급된다.
5. **거부 목록**: `..` 세그먼트, `.` 세그먼트, 빈 세그먼트, 드라이브 문자(`C:`), NUL, 개행·탭, 1,024자 초과. 실측에서 개행·탭 이름은 0건이지만 거부는 넣는다.
6. **대소문자는 보존하고 구분한다.** 리눅스 파일시스템이 그렇다. 실측에서 대소문자만 다른 형제는 0건. 다만 새 규칙이 기존 규칙과 대소문자만 다르면 **화면이 경고**한다. SMB 로 들어온 사람은 대소문자를 구분하지 않으므로 헷갈릴 여지가 남는다.
7. **심볼릭 링크는 판정 전에 realpath 로 푼다.** 푼 결과가 루트 밖이면 `hidden` 과 같게 다룬다. 실측에서 심링크는 0건이지만, 규칙을 만든 뒤에 누가 만들 수 있다.
8. **규칙 문자열로 파일시스템에 접근하지 않는다.** 실제 접근은 항상 `readdir` 가 준 이름으로 한다. 규칙은 비교에만 쓴다. 이것이 NFC/NFD 불일치가 실제 접근을 깨뜨리지 않게 하는 장치다.

**이름이 바뀌면 규칙은 고아가 된다.** 이 기능의 가장 큰 함정이다. `숨김` 규칙이 달린 폴더의 이름을 NAS 에서 바꾸면 규칙이 아무것도 가리키지 않게 되고, **그 폴더는 다시 보이게 된다.** 완전한 방지책은 없다(폴더에 안정적 id 가 없다). 완화 둘:

- **기본 자세를 숨김으로 둔다**(6.2). 그러면 이름이 바뀐 폴더는 규칙이 없는 폴더가 되어 다시 숨겨진다.
- **고아 규칙[<sup>10</sup>](#g10) 점검**을 관리 화면에 둔다. 존재하지 않는 경로를 가리키는 규칙을 목록으로 보여 주고, 운영자가 옮기거나 지운다.

## 6. 판정 알고리즘

### 6.1 입력과 출력

```text
입력: (요청자 신원, scope_root, folder_path)
      요청자 신원 = { profileId, gatewayRole, departments[], isSuperAdmin }
출력: "hidden" | "read" | "write"
```

### 6.2 순서

```text
0) 시스템 관리자면 "write". 부서 게이트와 같은 관례로, 게이트 자체를 만들지 않는다.
1) 경로를 정규화한다(5.2). 실패하면 "hidden".
2) 그 경로와 모든 조상 경로를 깊은 쪽부터 훑는다.
     folder_path = "a/b/c" 이면  "a/b/c" -> "a/b" -> "a" -> ""
   각 단계에서:
     2-1) 그 단계에 걸린 규칙 중 요청자에게 해당하는 것만 고른다.
          - subject_kind="user"       : subject_id == profileId
          - subject_kind="department" : subject_id 가 요청자 부서 집합에 있다
          - subject_kind="role"       : subject_id == 요청자 역할
          - 조상 단계에서는 inherit=1 인 것만 본다. 정확히 그 폴더면 inherit 무관.
     2-2) 고른 것이 없으면 다음(더 얕은) 단계로 간다.
     2-3) 고른 것이 있으면 여기서 끝낸다:
          a) 종류가 더 구체적인 것이 이긴다:  user > department > role
          b) 같은 종류가 여럿이면(= 부서를 여럿 가진 사람) 더 강한 제한이 이긴다:
             hidden > read > write
3) 아무 단계에서도 규칙을 못 찾으면 그 scope_root 의 기본값을 쓴다. 기본값은 "hidden".
```

### 6.3 왜 이 순서인가

**경로가 주체보다 먼저다.** 사용자 요구가 "하위 폴더도 개별 지정 가능(상위 상속 + 개별 덮어쓰기)" 이다. 주체를 먼저 보면 부서 규칙 하나가 상위에 있을 때 하위의 개별 지정이 영영 이기지 못한다. 그러면 "개별 덮어쓰기" 가 성립하지 않는다.\
반대 순서의 손해는 이렇다. `06_박정현` 전체를 그 사람에게 `read` 로 열어 두고, 그 아래 `12. 보안폴더` 를 부서 규칙으로 `hidden` 으로 잡았다고 하자. 경로 우선이면 보안폴더만 가려진다. 주체 우선이면 개인 규칙이 이겨 보안폴더가 열린다. 뒤쪽은 사고다.

**같은 경로에서는 개인이 부서를 이긴다.** 예외는 사람 단위로 생긴다. "김OO 만 이 폴더를 못 본다"·"김OO 만 이 폴더를 본다" 를 표현할 자리가 개인 규칙이고, 그것이 부서 규칙에 지면 표현할 방법이 사라진다.

**같은 종류가 여럿이면 더 강한 제한이 이긴다.** 사람이 부서를 둘 가졌을 때 부서를 하나 더 넣는 것이 권한을 넓히면 안 된다. 부서 경계 문서의 원칙 "부서는 상한을 넓히지 않고 좁히기만 한다"(AUTH-DEPARTMENTS 3절)를 그대로 잇는다. 역할은 사람마다 하나라 이 경우가 생기지 않는다.

**규칙이 없으면 숨김이다.** 화이트리스트 원칙(AUTH-DEPARTMENTS 13.2)의 반복이다. 목록에서 빠뜨린 폴더가 열린 문이 되는 구조를 만들지 않는다. 실측한 트리가 37,356 폴더이고 개인 공유마다 `보안폴더` 가 있으므로, 빠뜨림은 늘 일어난다고 봐야 한다.\
대가는 초기 설정 비용이다. 그래서 화면에 "이 폴더와 하위 전체에 적용" 을 두어 공유 하나를 한 번에 여는 조작을 1클릭으로 만든다(8.4).

### 6.4 숨김이 뜻하는 것

숨김 폴더는 다음 **어디에서도** 나오지 않는다. 하나라도 새면 숨김이 아니다.

| 표면            | 어떻게 막히나                                                        |
| --------------- | -------------------------------------------------------------------- |
| 폴더 트리       | `entries` 배열에서 빠진다. 직접 경로를 넣어도 404                    |
| 파일 목록·열기  | 3.2 의 네 메서드가 판정 뒤에 읽는다. 거부는 404                      |
| 문서 미리보기   | 같은 경로를 지난다                                                   |
| 지식 색인       | 사이드카를 만들지 않고, 이미 있으면 지운다                           |
| 채팅 검색       | 사이드카가 없으므로 결과에 없다                                       |
| 에이전트 요약   | 3단계에서 런의 루트 집합에 들어가지 않는다. 그전까지는 에이전트 워크스페이스가 상한 |
| 감사 화면       | 거부는 남지만 경로 문자열은 512자에서 잘린 채 관리자만 본다          |

### 8.2 배치

```text
+---------------------------+--------------------------------------------------+
| 폴더                      | /mnt/nas/00_공용폴더/#업무양식                    |
|                           |                                                  |
| v 00_공용폴더        읽기 | [부서]  [역할]  [개인]                           |
|   > #경영회의        숨김 |                                                  |

|     > 작업중         숨김 | 품질보증    (숨김) (읽기) (쓰기)  [ ] 이 폴더만  |

| > 06_박정현          읽기 | 실제 적용: 읽기                                  |
|                           |   근거: #업무양식 의 부서 규칙(연구개발, 상속)   |
| [ ] 숨김도 표시           |                                                  |
+---------------------------+  [이 폴더와 하위 전체에 적용]  [규칙 지우기]      |
```

- **왼쪽 트리**: 지연 확장. 노드를 펼칠 때만 `departments.folders.list` 를 그 경로로 부른다(500개 상한이 이미 있다). 각 노드 오른쪽에 현재 유효 권한을 칩으로 표시하고, 상속으로 정해진 것은 `(상속)` 으로 흐리게 둔다.
- **관리자에게는 숨김 폴더도 보인다.** 안 보이면 숨김을 풀 수 없다. 다만 흐리게 표시하고, 체크박스로 감출 수 있게 둔다.
- **오른쪽 편집**: 부서·역할·개인 세 탭. 각 행이 주체 하나이고, 권한은 3택 1 세그먼트, 상속은 체크박스 하나.
- **실제 적용 미리보기**가 반드시 있어야 한다. 6.2 의 판정을 그대로 돌려 "이 폴더에서 이 주체에게 실제로 적용되는 값" 과 **그 근거가 된 규칙의 경로**를 함께 보여 준다. 상속과 덮어쓰기가 섞이면 사람이 머릿속으로 못 푼다.
- **개인 탭**은 사람을 검색해서 행을 추가하는 모양이다. 부서 탭처럼 전원을 나열하지 않는다.

### 8.3 트리 컴포넌트를 무엇으로 만드나

| 안                                      | 판단                                                                                             |
| --------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 새 npm 트리 라이브러리                  | **미채택.** UI 는 Lit 이고 React 트리 라이브러리가 안 맞는다. 번들 상한(215 KiB gz)도 위험         |
| `@awesome.me/webawesome` 의 `wa-tree`   | 이미 의존성에 들어 있으나 저장소에서 아직 한 번도 import 하지 않았다. 쓰면 청크가 얼마나 느는지 계측이 먼저다 |
| 손으로 만든다                           | **채택 권고.** 약 200줄. `department-access-panel.ts:135` 의 브라우저 렌더와 `app-sidebar-session-tree.ts` 의 사이클 가드 패턴을 재료로 쓴다 |

### 8.4 일괄 적용

"이 폴더와 하위 전체에 적용" 은 **`inherit=1` 규칙 하나를 쓰고, 그 아래에 있는 같은 주체의 규칙을 지운다.** 지우기 전에 무엇이 지워지는지 목록으로 보여 주고 확인을 받는다.\
하위 규칙을 남겨 두면 "전체에 적용했는데 몇 개가 다르다" 가 되어 사람이 원인을 못 찾는다.

## 9. 단계 분할

### 9.0 선행 (반나절, 코드 아님)

컨테이너에 NAS 신원을 준다(4.2). NAS 에 읽기 전용 그룹을 만들고, 대상 공유의 ACL 에 그 그룹을 넣고, compose 의 게이트웨이 서비스에 `group_add` 를 넣는다. 그 다음 실제 공유를 `:ro` 로 마운트한다(DEPLOY 11.4 의 절차를 바인드 마운트로 바꾼 판).\

### 12.1 0단계: NAS 신원과 마운트

**그룹 2개를 신설했다.** 구성원은 없다. 컨테이너 프로세스에만 보조 그룹으로 주려고 만든 것이다.

| `openclaw-rw` | 65541 | `rwxpdDaARWc--:fd--` | 아직 없다. 3단계에서 쓰기를 열 때 |

실물은 NAS 의 `/volume1/docker/openclaw/docker-compose.nas.yml`(백업 `.bak-20260909-acl`).
로컬 개발용 `chris-local/docker-compose.ixauth.yml` 은 샘플 트리 그대로 두었다.

**감사.** 새 kind 를 만들지 않았다. 규칙 변경은 `admin_action` 의 `action` 값
`folder-rule-set`·`folder-rule-clear` 로, 숨김 폴더 열람 시도는 `access_denied` 의
`surface: "folder-tree"` 로 남는다. 화면 필터 목록(`ui/src/pages/audit/audit-rows.ts`)은

(3.6 이 제안한 스네이크 표기 `folder_rule_set` 이 아니다).

**화면.** `/settings/folders`. 왼쪽 지연 확장 트리 + 오른쪽 권한 편집(부서·역할·개인 탭).
각 주체 행에 실제 적용 권한과 근거 경로를 함께 보여 준다. 미리보기 선택기로 "이 사람에게 어떻게
보이나" 를 고르면 왼쪽 트리가 그 사람의 시야로 다시 그려진다. 숨김이 실제로 먹는지 확인하는

2. **미리보기가 숨김 폴더를 그대로 보여 줬다.** 관리자 시야에서는 숨김도 보여야 하는데 그

   빼고 직접 열려는 시도도 같은 거부로 답하게 고쳤다(커밋 `c6597af275a`).

사람이 파일을 실제로 읽는 자리에 걸었다.

### 13.1 파일 목록·열기·미리보기

**게이트 하나를 새로 만들었다**(`src/gateway/folder-access-guard.ts`, 125줄).
요청자 신원과 브라우징 루트를 받아 그 루트 아래 경로마다 "보이나" 를 답한다.

| 무엇 | 어디 |
| --- | --- |
| 게이트 | `src/gateway/folder-access-guard.ts` `prepareFolderAccessGate()` |
| 판정 재사용 | `folder-access-policy.ts` 에 `buildFolderRuleIndex()`·`resolveFolderAccessIndexed()` 를 더했다 |
| 세션 파일 목록 | `server-methods/sessions-files.ts` `buildListResult()` -> `buildBrowserResult()`·`searchBrowserEntries()` |
| 세션 파일 열기 | 같은 파일 `findSessionFile()` |
| 세션 파일 쓰기 | 같은 파일 `sessions.files.set`. 마운트가 `:ro` 라 실제 쓰기는 없지만 오류가 존재를 알리지 않게 한다 |
| 문서 미리보기 | 별도 손질 없음. `sessions.files.get` 이 읽기를 허락한 뒤에만 `sessions-files-document.ts` 로 간다 |
| 에이전트 파일 | `server-methods/agents.ts` `agents.files.list`·`get` |
| 워크스페이스 브라우저 | `server-methods/agents-workspace.ts` `agents.workspace.list`·`get` |

**`client` 를 안 받던 문제는 구조분해에 한 단어를 더하는 것으로 끝났다.** 3.2 가 걱정한
`sessions.files.list` 의 시그니처 변경은, 실제로는 핸들러 인자에 이미 `client` 가 들어와 있고
그 핸들러만 꺼내 쓰지 않고 있던 것이었다. 신원은 R 이 `department-access.ts` 에 실어 둔
`ixAuthDepartments`(프로필·역할·부서)를 그대로 읽는다. 감사용 bag 은 읽지 않는다.

**적용 범위를 좁게 잡은 것이 이 변경의 핵심이다.** 게이트는 다음 넷 중 하나라도 해당하면
아예 만들어지지 않고, 그때 모든 호출자는 이전과 완전히 같게 동작한다.

1. 브라우징 루트가 공유 마운트(`/mnt/nas`) 밖이다. 에이전트 홈 워크스페이스가 여기 해당한다.
2. 연결에 검증된 신원이 없다(호스트 셸·운영자 토큰).
3. 시스템 관리자다.
4. 루트가 realpath 로 풀리지 않는다.

이 조건이 없으면 "규칙 없음 = 숨김" 이 에이전트 자기 워크스페이스까지 덮어 제품이 닫힌다.

**거부는 없는 파일과 같다.** 목록에서는 빠지고, 직접 열기는 `session_file_not_found` 로
답한다. 숨김 전용 오류를 따로 만들지 않았다. 거부는 `access_denied` 의
`surface: folder-read` 로 원장에 남는다(R 의 `folder-tree` 와 짝이다).

**검색도 같이 막았다.** 파일 패널의 검색은 워크스페이스를 재귀로 훑는다. 숨김 폴더로는
내려가지 않는다. 결과만 걸러 내면 "몇 건" 이라는 숫자로 존재가 샌다.

### 13.2 지식 색인

**색인 시점에는 사람이 없다.** 크론이 돌리고, 결과 사이드카는 메모리 검색이 읽는 공용 풀
하나에 쌓이며, 그 풀에서 나갈 때 사람별 필터가 걸리지 않는다. 그래서 그 시점에 낼 수 있는
판정은 요청자에 대한 것이 아니라 **폴더에 대한 것** 하나다.

> **규칙**: 규칙이 명시적으로 누군가에게 열어 준 폴더만 색인한다. 아무도 못 보는 폴더는
> 이름조차 읽지 않는다.

근거는 셋이다.

1. **읽을 사람을 특정할 수 없다.** 사이드카는 공용 풀이고 질의 시점 필터가 없다. 유일하게
   성립하는 문장이 "이 폴더를 볼 수 있는 주체가 하나라도 있는가" 다.
2. **비용.** 실측 트리가 37,356 폴더다. 걷고 나서 거르면 숨김 폴더의 파일 이름을 전부 읽고
   버리게 된다. 걷기 자체를 자르면 그 비용이 0 이다.
3. **회수가 공짜로 따라온다.** 걷지 않은 폴더의 파일은 `known` 집합에 들어가지 않고,
   `findOrphanSidecars()` 가 이미 "원본을 못 찾은 사이드카" 를 지운다. 나중에 숨김이 된
   폴더의 사이드카는 다음 동기에서 저절로 회수된다. 별도 장치를 만들지 않았다.

**사이드카 frontmatter 의 원본 경로로 판정하는 안은 채택하지 않았다.** `sourcePath` 가 있으니
색인 폴더 쪽에서 거꾸로 훑는 것도 가능하지만, 그러면 판정이 두 곳(걷기와 정리)에 생기고 두
답이 갈릴 수 있다. 걷기 하나만 판정하고 정리는 그 결과를 따라가는 지금 모양이 판정 지점을
하나로 유지한다.

**공유를 통째로 비우지 않기 위한 안전장치.** 규칙 표가 그 공유를 **한 번도 언급하지 않았으면**
(공유 자체·그 하위·상속되는 조상 어디에도 규칙이 없으면) 이 기능이 그 공유에 대해 켜지지
않은 것으로 보고 종전대로 색인한다. "규칙이 없다" 를 "전부 비밀" 로 읽으면 운영자가 손대지도
않은 공유의 색인이 첫 규칙 하나에 통째로 비워진다. 한 번이라도 규칙이 걸린 공유는 그 순간부터
기본값이 숨김이고, 그것이 이 기능의 의도다.

| 무엇 | 어디 |
| --- | --- |
| 필터 | `src/knowledge/folder-rule-filter.ts` `prepareKnowledgeFolderFilter()` |
| 판정 | `folder-access-policy.ts` `isFolderVisibleToAnySubject()` |
| 걷기 자르기 | `src/knowledge/plan.ts` `scanKnowledgeSource({ allowDirectory })` |
| 새 제외 사유 | `src/knowledge/types.ts` `folder-hidden`. 폴더당 한 줄이고 파일마다가 아니다 |
| 옵션 | `syncKnowledgeIndex({ respectFolderRules })`, CLI `--no-folder-rules` |
| 요약 | `KnowledgeSyncSummary.folderRulesApplied` 와 명령 출력 한 줄 |

**부수 효과**: `#recycle`·`@eaDir`·`@tmp` 는 판정 모듈이 이미 숨김으로 답하므로, 규칙이 걸린
공유에서는 색인에서도 빠진다. 그전에는 색인되고 있었다.

**남는 구멍은 적어 둔다.** 한 부서에 열어 준 폴더와 다른 부서에 열어 준 폴더가 같은 풀에
들어간다. 색인 자체는 부서 경계가 아니다. 그 경계는 에이전트의 것이고 도구 안에서 닫는 것이
3단계다.

### 13.3 고아 규칙 점검

RPC 둘을 더했다.

| 메서드 | 스코프 | 하는 일 |
| --- | --- | --- |
| `folders.rules.orphans` | `operator.read`, 등급 판정은 핸들러 | 가리키는 것이 없어진 규칙 목록 |
| `folders.rules.orphansClear` | 같음, `CONTROL_PLANE_WRITE` | 일괄 삭제 |

고아는 두 종류다. **`missing-folder`** 는 폴더가 공유에서 사라졌거나 이름이 바뀐 것이고,
**`missing-subject`** 는 규칙이 가리키는 부서·계정이 없어진 것이다(5.1 이 "지우지 않고 화면에
고아로 표시한다" 고 정한 그것이다).

**자동 복구는 하지 않는다.** 이름 변경과 삭제를 서버가 구분할 수 없고, 짐작해서 규칙을 다시
붙이면 누군가 닫아 둔 폴더를 조용히 여는 일이 된다. 그래서 목록과 삭제뿐이다.

**삭제는 두 번 묻고, 서버가 다시 잰다.** 화면이 보낸 목록을 믿지 않고 삭제 시점에 다시
수집해서 그때도 고아인 것만 지운다. 확인하는 사이에 폴더가 돌아왔으면 그 규칙은 남는다.
마운트가 없는 상태에서는 모든 규칙이 고아로 보이므로 아무것도 지우지 않고 거부한다.
삭제는 `admin_action` 원장에 `orphanReason` 과 함께 한 건씩 남는다.

화면은 `/settings/folders` 아래 절이다(`ui/src/pages/folders/folder-orphans-panel.ts`).

### 13.4 설계와 달라진 것 (2단계)

| 설계 | 실제 | 왜 |

| `sessions.files.list` 핸들러 시그니처를 바꿔야 한다(3.2) | 구조분해에 `client` 한 단어 | 인자에 이미 들어와 있었다 |
| 문서 미리보기를 따로 막는다(7절 7번) | 따로 손대지 않았다 | 같은 핸들러의 파일 읽기를 지나므로 자동으로 닫힌다 |

### 13.5 2단계 뒤에도 아직 아닌 것

- **에이전트가 도구로 읽는 파일**(3.4). 3단계다. 도구 실행 컨텍스트에 사람이 없다는 사실이
  그대로다.
- **쓰기**(4.4). 마운트가 `:ro` 이고 네 조건이 서기 전에는 열지 않는다.
- **`media_read` 가 여는 색인 사이드카.** 색인 시점 제외로 범위는 좁아졌지만, 사이드카가
  이미 있는 폴더가 나중에 숨김이 되면 다음 동기까지 남는다(11절의 "색인 반영 지연" 그대로).
- **파일 패널이 NAS 를 보려면 에이전트 워크스페이스가 공유 안에 있어야 한다.** 납품 구성은
  에이전트가 `main` 하나이고 그 워크스페이스는 컨테이너 홈이다(O 단계). 즉 지금 배치에서
  13.1 의 게이트가 실제로 걸릴 표면은 아직 없고, 공유를 에이전트에 물리는 날 그대로 작동한다.
  V 단계 실측은 임시 에이전트를 하나 붙여 확인하고 되돌리는 방식으로 했다(13.6).

### 13.6 운영 실측 (2026-09-09, `https://jinbio.botops.cloud`)

**실측을 위해 임시 에이전트를 하나 붙였다.** 납품 구성은 에이전트가 `main` 하나이고 그
워크스페이스는 컨테이너 홈이라, 게이트가 걸릴 표면이 없다(13.5). NAS 의 설정 템플릿에
`nascheck`(워크스페이스 `/mnt/nas/00_공용폴더`, `skipBootstrap`)를 넣고 확인한 뒤 지웠다.
읽기 전용 워크스페이스로도 세션 생성과 응답에 문제가 없다는 것이 함께 확인됐다.

규칙은 관리자 `admin.test`(관리자 등급, 부서 연구개발·품질)로 걸었다. 이 사람은 시스템

2. **열이 한 글자 폭으로 눌렸다.** 8열 양식이 좁은 패널에 맞춰 줄어들었다. 표에

세 개(`00_공용폴더` 연구개발 읽기, `#경영회의` 연구개발 숨김, 그리고 그 짝)로 돌아갔다.
NAS 의 ACL·그룹·compose 는 R 이 만든 그대로 한 줄도 건드리지 않았다.

**곁가지 확인**: 공유 밖 워크스페이스는 종전과 똑같다. `main` 의 세션에서
`sessions.files.list` 가 `/home/node/.openclaw/workspace` 의 7개 항목을 그대로 돌려준다.
게이트가 넓게 걸렸다면 여기가 먼저 비었을 것이다.

## 14. 폴더 트리 인덱싱과 공유별 기본 권한 (2026-09-09, X 단계)

### 14.1 왜 느렸나 (실측)

사용자가 "폴더 트리 조회가 되게 느리다" 고 했다. 원인은 폴더 수가 아니라 **한 단계를 그리는 비용**이었다.

기존 `listDepartmentFolders()` 는 `readdir` 로 이름을 받은 뒤 **이름 하나마다** `realpath`+`stat` 를 불러
폴더인지 확인했다. 공유 폴더에는 파일이 수천 개 든 폴더가 흔하고, 그 전부에 대해 시스템 호출 두 번을
낸다. 2026-09-09 컨테이너 안 실측이다.

| 폴더 | 항목 수 | `readdir` 만 | `readdir` + 항목마다 `realpath`·`stat` |
| --- | --- | --- | --- |
| 항목이 가장 많던 폴더 (00_공용폴더 아래) | 3,127 | 5 ms | **856 ms** |
| `/mnt/nas` (공유 11개) | 11 | 3 ms | 3 ms |
| `00_공용폴더` (하위 18) | 18 | 3 ms | 5 ms |

폴더가 적은 단계는 원래 빠르다. 느린 것은 **파일이 많은 폴더**이고, 거기에 사람이 대기하는 시간이
NAS 의 2코어와 겹친다. 여기에 터널을 지나는 왕복이 매 펼침마다 한 번씩 더 붙는다.

### 14.2 고친 것 두 가지

1. **라이브 조회를 `readdir(withFileTypes)` 로 바꿨다.** 항목 종류가 목록과 함께 오므로 파일에는
   시스템 호출이 더 붙지 않는다. `realpath` 는 심링크 항목에만 낸다. 탈출 검사는 그대로다.
   같은 폴더가 856 ms -> 5 ms 다. 부서 화면의 워크스페이스 선택기도 같이 빨라진다.
2. **폴더 구조를 미리 훑어 상태 DB 에 저장한다.** 화면은 저장본을 읽고, 저장본이 없는 가지에서만
   지금처럼 NAS 를 직접 읽는다. 저장본이 비어도 화면은 종전과 똑같이 동작한다.

### 14.3 저장하는 것

R 단계가 쓴 상태 DB 관례를 그대로 따른다(기능 지역 추가 스키마, 첫 기록 때 만든다).

| 표 | 내용 |
| --- | --- |
| `folder_tree_nodes` | 공유 루트, 경로, 부모 경로, 이름, 절대경로, 자식 수, 읽을 수 있었는지, **자식을 읽은 시각**, 이 행을 본 시각 |
| `folder_tree_scans` | 마운트당 한 행. 마지막 훑기의 시작·끝·소요·폴더 수·못 읽은 폴더 수·잘림 여부 |

**폴더만 담고 파일은 담지 않는다.** 파일 이름은 시간마다 바뀌고 트리는 그것을 그리지 않는다.
행 수가 스무 배가 되는 대가로 얻을 것이 없다.

**`자식을 읽은 시각` 이 따로 있는 이유**는 "하위가 없는 폴더" 와 "아직 아무도 안 읽은 폴더" 를
구분해야 해서다. 구분하지 못하면 빈 폴더는 영원히 미확인으로 남아 누를 때마다 NAS 를 읽는다.

### 14.4 갱신 방식

검토한 세 가지 중 **(가) 주기 실행 + (다) 관리자 새로고침** 을 골랐다. (나) "펼칠 때 저장본을 먼저
보여 주고 뒤에서 갱신" 은 넣지 않았다. 사람이 펼칠 때마다 NAS 훑기가 따라붙어 결국 지금과 같은
부하가 되고, 화면이 눌린 뒤에 바뀌는 동작은 설명하기도 어렵다.

| 갈래 | 언제 | 무엇 |
| --- | --- | --- |
| 주기 | 매일 03:20 (호스트 cron) | 공유 전체를 다시 훑는다. [DEPLOY.md](DEPLOY.md) 12.3 |
| 새로고침 | 관리자가 누를 때 | **고른 가지만** 다시 훑는다. 아무 폴더도 고르지 않았으면 전체 |
| 저장본 없음 | 항상 | 그 가지는 NAS 를 직접 읽는다. 화면이 비지 않는다 |

**겹치기 방지는 상태 DB 행이다.** 훑기를 시작할 때 `folder_tree_scans` 에 "끝나지 않음" 으로 행을
쓰고, 다른 훑기는 그 행을 보고 물러난다. 프로세스 안의 플래그가 아니라 행인 이유는 크론이 도는
CLI 와 화면을 받는 게이트웨이가 **다른 프로세스**이기 때문이다. 두 시간이 넘은 claim 은 죽은 실행이
남긴 것으로 보고 걷어낸다(`deploy.sh` 의 잠금 규칙과 같다).

### 14.5 훑기가 지키는 것

- **동시성 2.** NAS 가 2코어이고 낮에는 회사의 파일 서버다. 상한은 8이다.
- **보안폴더에서 멈추지 않는다.** `readdir` 이 거부되면 그 폴더를 "읽을 수 없음" 으로 적고 다음으로
  간다. 12.1 의 일곱 폴더가 여기 해당한다.
- **`#recycle`·`@eaDir`·`@tmp` 는 훑지 않는다.** 판정 모듈의 제외 이름을 그대로 쓴다.
- **없어진 폴더의 행은 지운다.** 이번 훑기가 보지 못한 행만 지우고, **규칙은 건드리지 않는다.**
  없어진 폴더의 규칙은 종전대로 고아 규칙 화면(13.3)이 다룬다.
- 진행 상황을 2,000 폴더마다 로그에 남긴다. 상한은 20만 폴더·깊이 40이다.

### 14.6 명령과 화면

```bash
openclaw folders scan [--path <가지>] [--concurrency 2] [--json]
openclaw folders status      # 마지막 훑기가 언제, 몇 폴더였는지
openclaw folders clear       # 저장본을 버린다. 화면은 다시 NAS 를 직접 읽는다
```

게이트웨이 RPC 를 쓰지 않아 ix-auth 배포의 컨테이너 안에서 그대로 돈다(`cron add` 가 막히는 것과
대비된다. DEPLOY.md 12.3). 화면(`/settings/folders`)에는 트리 위에 **마지막 갱신 시각과 폴더 수,
새로고침 단추**가 붙는다. 새로고침은 훑기를 띄우고 곧바로 답하며, 화면이 3초마다 상태를 물어
끝나면 열려 있던 가지를 다시 그린다. RPC 는 `folders.tree.refresh` 하나가 늘었다.

### 14.7 실측 (2026-09-09, 운영 NAS)

**전체 훑기** (`openclaw folders scan`, 동시성 2, 컨테이너 안)

| 항목 | 값 |
| --- | --- |
| 저장한 폴더 | **19,136** (공유 11개 = 실제 9 + 샘플 `rnd`·`qa`) |
| 소요 | **17.5초** (첫 실행) · 10.7~11.7초 (반복) · 34.9~42.8초 (문서 색인이 2코어를 채우고 있을 때) · 121초 (색인과 이미지 배포가 겹쳤을 때) |

2절이 적은 37,356 폴더와 다른 이유는 그 값이 호스트에서 root 로 센 것이기 때문이다.
**컨테이너가 볼 수 있는 폴더는 19,136개**이고, 차이는 전부 `보안폴더` 안이다.

기계가 한가하면 10초대, 색인이 코어를 채우면 40초대, 거기에 이미지 배포까지 겹치면 2분이다.
어느 쪽이든 사람이 기다리는 시간이 아니라 새벽 크론이 쓰는 시간이다.

**화면 체감** (관리자 화면에서 폴더 하나를 펼쳐 목록이 그려질 때까지, 터널 왕복 포함)

| --- | --- | --- | --- |
| `00_공용폴더` (하위 16) | 148 ms | 125 ms | |

| 항목 3,127개짜리 폴더 | 펼치기 단추가 있고, 눌러야 "하위 없음" 을 안다 | **단추가 없다**(잎으로 그린다) | 저장본이 자식 수를 안다 |

왕복 지연이 100 ms 쯤이라 그 아래로는 내려가지 않는다. **실제로 사라진 비용은 서버 쪽이다**:
같은 폴더의 디렉터리 읽기가 856 ms 에서 5 ms 가 됐고(14.1~14.2), 그 뒤로는 NAS 를 아예 읽지
않는다. 파일만 많은 폴더가 잎으로 그려지는 것이 사람 눈에 가장 크게 보이는 변화다.

### 14.8 공유별 기본 권한 (2026-09-09 사용자 확정)

사용자 지시는 두 번에 걸쳐 왔고 뒤의 것이 정본이다.

1. "민감정보 즉 인사 급여 이화정 폴더는 이화정 사용자 즉 관리자만 볼 수 있어야 해."
2. "디자인PC는 모두가 접근 가능해야 돼. 이영준한의원 폴더도 마찬가지고. **이화정 폴더만 관리자야.**"

**관리자 전용은 `01_이화정` 하나이고 나머지 여덟 공유는 전 직원이 본다.** 지금 걸린 규칙이다(32행).

| 공유 | 규칙 (전부 상속) | 직원·중재자·임원 | 색인 |
| --- | --- | --- | --- |
| `00_공용폴더` | 직원·중재자·임원 = 읽기, 연구개발 = 읽기(R 단계 잔존) | 보인다 | 대상 |
| `00_공용폴더/#경영회의` | 직원·중재자·임원 = 숨김, 연구개발 = 숨김 | 안 보인다 | 제외 |
| `01_이화정` | 직원·중재자·임원 = **숨김** | 안 보인다 | **제외** |
| `02_최병만` `03_장혜린` `04_김서희` `05_이대훈` `06_박정현` | 직원·중재자·임원 = 읽기 | 보인다 | 아직 안 함 |
| `디자인PC` `이영준한의원` | 직원·중재자·임원 = 읽기 | 보인다 | 아직 안 함 |
| `qa` `rnd` (샘플 마운트) | 규칙 없음 | 안 보인다(기본값) | 제외 |

**각 공유의 `보안폴더` 7개는 앱 규칙과 무관하다.** NAS ACL 이 컨테이너에 그 폴더를 열어 주지
않으므로(12.1) 상위 폴더에 읽기를 줘도 **안이 비어 있다.** 트리에는 이름이 그대로 보이고(상위
폴더를 읽으면 이름은 나온다) 그 아래로는 아무것도 나오지 않으며, 색인도 한 파일도 만들지 못한다.
이름까지 감추려면 그 폴더에 숨김 규칙을 따로 걸어야 한다.

**왜 `01_이화정` 에 "관리자 읽기" 를 주지 않았나.** 이 표에서 관리자에게 읽기를 주면 그 폴더가
`isFolderVisibleToAnySubject()` 에서 "볼 수 있는 주체가 있다" 가 되어 **문서 색인 대상이 된다**(13.2).
색인 사이드카는 사람별 필터가 없는 공용 풀이고 공용 비서가 그 풀을 검색한다. 즉 인사·급여를
색인하는 순간 그 내용이 비서의 검색·요약을 통해 **누구에게나** 새어 나갈 수 있다. 그래서 이 공유에는
아무에게도 읽기를 주지 않고, 관리자는 다음 두 가지로 본다.

1. **폴더 권한 화면의 트리.** 관리자·시스템 관리자에게는 숨김 폴더도 그대로 보인다(그러지 않으면
   숨김을 되돌릴 수 없다). 지금 배치에서 관리자가 앱으로 그 공유를 보는 경로가 이것이다.
2. **NAS 파일 탐색기.** 사람이 자기 NAS 계정으로 직접 여는 경로는 이 규칙과 무관하다(11절).

명시적인 "관리자 읽기" 가 필요하면 규칙 한 줄이면 되지만, **그 순간 그 공유가 색인 대상 자격을
갖는다.** 그때는 `nightly-index.sh` 의 `SHARES` 에 그 공유를 넣지 않는 것이 두 번째 방어선이다.

**`#경영회의` 를 임원에게도 숨긴 것은 판단이다.** 경영회의 자료는 성격상 민감하고, 임원에게 열면
같은 이유로 색인 풀에 들어간다. 임원이 앱에서 그 폴더를 봐야 한다면 규칙 한 줄을 읽기로 바꾸면
되지만, 바꾸는 순간 색인 범위에 들어간다는 것을 알고 바꿔야 한다.

**역할 셋에만 규칙을 적는 이유.** 관리자·시스템 관리자는 규칙과 무관하게 숨김 폴더까지 보므로
행을 만들 필요가 없다. 직원·중재자·임원 셋이 이 회사의 일반 사용자 전부다.

### 14.8-1 NAS 자체 색인은 쓰지 않는다 (2026-09-09 조사)

이 NAS 에는 Universal Search(SynoFinder)가 켜져 있고 공유 여덟 개를 **본문까지** 색인하고 있다.
"그걸 쓰면 되지 않나" 에 대한 답과 근거는 [KNOWLEDGE.md](KNOWLEDGE.md) 8-2 에 있다. 요약하면,
폴더 트리는 우리 훑기가 17.5초라 쓸 이유가 없고, 문서 본문은 NAS 색인 쪽이 대부분 비어 있으며
(한글 문서는 8%만 본문이 있다) 접근 경로도 호스트 root 또는 새 DSM 계정을 요구한다. 설계는
바꾸지 않았다.

**운영에 알려 둘 것 하나**: `01_이화정` 도 DSM 색인에는 본문까지 들어 있다. 우리 앱은 그 공유를
읽지 않지만, NAS 계정으로 DSM 검색을 쓰는 사람에게는 보인다. 그 경계는 NAS 관리자의 몫이다.

### 14.9 다음에 할 것

- **실제 직원 계정이 생기면 개인 규칙을 더한다.** 이화정 본인 계정이 생기면 `01_이화정` 에 개인
  읽기를 준다(개인 > 부서 > 역할이라 역할 숨김을 이긴다). 그 순간 그 공유가 색인 대상 자격을
  가지므로, 색인에서 빼려면 `nightly-index.sh` 의 `SHARES` 에 넣지 않는다.
- **나머지 여덟 공유의 색인**은 `00_공용폴더` 실측으로 일정을 잡는다([KNOWLEDGE.md](KNOWLEDGE.md) 7.2).
- **폴더 이름을 바꾸면 저장본과 규칙이 함께 어긋난다.** 저장본은 다음 훑기가 스스로 고치고,
  규칙은 고아 규칙 화면에서 사람이 정리한다.

## 용어 설명

1. <a id="g1"></a>**컨텍스트(도구 실행)** - 모델이 도구를 부를 때 그 호출과 함께 전달되는 정보 묶음. 여기에 무엇이 들어 있느냐가 도구 계층에서 무엇을 판정할 수 있는지를 정한다.
2. <a id="g2"></a>**게이트웨이** - 모든 요청이 먼저 닿는 앞단 서버. 이 제품에서는 화면·인증·에이전트 실행을 한꺼번에 맡는 본체다.
3. <a id="g3"></a>**청크** - 브라우저가 한 번에 내려받는 자바스크립트 묶음 단위. 이 저장소는 가장 큰 묶음의 압축 크기에 상한을 두고 있다.
4. <a id="g4"></a>**바인드 마운트** - 호스트의 어떤 폴더를 컨테이너 안의 다른 경로에 그대로 비춰 주는 것. 파일을 복사하지 않고 같은 폴더를 두 이름으로 보는 방식이다.
5. <a id="g5"></a>**ACL** - 폴더나 파일마다 "누가 무엇을 할 수 있는가" 를 항목으로 적어 둔 목록. 사용자별·그룹별로 따로 적을 수 있어 소유자·그룹·기타 셋만 있는 옛 방식보다 세밀하다.
6. <a id="g6"></a>**보조 그룹** - 프로세스가 자기 주 그룹 말고 추가로 가지는 그룹. 권한 검사에서 이 그룹들도 함께 본다.
7. <a id="g7"></a>**정규화(유니코드)** - 같은 글자를 표현하는 방식이 여럿일 때 하나로 통일하는 것. 한글은 완성형 한 글자와 자모 여러 개로 나뉜 형태가 모두 가능해서, 통일하지 않으면 같은 이름이 다른 것으로 비교된다.
8. <a id="g8"></a>**사이드카** - 원본 문서 옆에 따로 만들어 두는 텍스트 사본. 여기서는 검색에 걸리게 하려고 만드는 마크다운 파일이다.
9. <a id="g9"></a>**지연 확장** - 트리에서 노드를 펼치는 순간에만 그 아래 목록을 가져오는 방식. 전체를 미리 내려받지 않아 큰 폴더에서도 화면이 뜬다.
10. <a id="g10"></a>**고아 규칙** - 가리키던 대상이 사라져 아무것도 적용되지 않게 된 규칙.

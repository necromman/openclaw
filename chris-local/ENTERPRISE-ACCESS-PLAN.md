# 기업용 사용자·조직·NAS 권한 관리 개선계획

작성: 2026-09-11 KST. 대상: `chris/main`, 분석 기준 커밋 `e7f06c80c2f`.

**권고 방향: IX-Auth를 유지하면서 NAS 권한을 가져올 원본으로 삼고, 앱 안에서 사용자·부서·접근 그룹·폴더를 연결해 관리한다.** 가져오기는 기존 권한의 초안을 만드는 일부터 시작한다. 지속 동기화와 AI 검색까지의 권한 적용은 별도 완료 조건을 가진 후속 작업이다.

이 프로젝트의 제품 기준은 **여러 직원이 함께 쓰는 기업용 AI 서비스**다. 관리자가 직원 한 명을 등록하고, 그 사람이 볼 자료를 확인하고, 퇴사 시 접근을 회수하는 일을 한 흐름으로 끝낼 수 있어야 한다.

이 문서는 분석·계획이다. 구현, 새 설정·DB 스키마 승인, NAS 설정 변경, 계정 생성, 초대 발송, 배포를 수행하지 않았다. 기존 정책의 변경안은 명시적으로 결정한 뒤 구현한다.

실측은 관리자 세션의 조회와 NAS 읽기 전용 명령으로 제한했다. 로그인·세션 생성에 따른 정상 이력 외에 계정/그룹/ACL 수정, 초대·CSV 등록, NAS 파일 쓰기, 트리 재색인, 서비스 재시작·배포는 수행하지 않았다. 실제 사내 문서 원문이나 AI 질의 결과는 수집하지 않았다. 따라서 **직원별 검색 누출이나 회수 실패를 실측으로 재현했다는 주장은 하지 않는다.**

재현 증적은 private `chris-server`의 `analysis/2026-09-11-enterprise-access/`에 보관한다. NAS 명령·응답은 `nas-platform.json`, `nas-access.json`, `nas-validation.json`, `nas-api.json`; 사이트 집계와 GET 상태는 `site-measurements.json`, 화면은 `site-*.png`. 원본 계정명·폴더명이 있는 캡처를 공개 포크로 복사하지 않는다. 운영 명령은 해당 저장소의 `logs/command-log.md`에 기록했다.

## 2. 현재 기반은 유지하고, 관리 단위를 바꾼다

### 2.1 이미 있는 기능

| 기반 | 현재 구현 | 개선 시 유지할 것 |
| --- | --- | --- |
| 사용자 관리 | 검색·역할/상태/부서 필터, 초대, CSV 등록, 상세, 부서/역할 변경, 세션 종료 | `ui/src/pages/users/`, `src/gateway/ix-auth-admin-users-*`의 기존 화면·BFF |
| 부서 관리 | IX-Auth의 `dept-` 그룹을 부서로 해석. 생성·표시명 수정·구성원·에이전트 연결 | 기존 부서 식별자와 가입 정보. 조직 개념을 버리고 다시 만들 필요 없음 |
| 폴더 관리 | 트리, 역할/부서/개인 규칙, 상속 표시, 주체 미리보기, 고아 규칙 정리 | `folder-access-policy.ts`의 단일 판정기, 트리 UI와 감사 기록 |
| 트리 성능 | SQLite에 폴더 스냅샷 저장, 펼친 단계 조회, 부분 새로고침 | 파일 트리 스냅샷과 요청 시 권한 계산의 분리 |
| 사용자 식별 | IX-Auth 계정과 Gateway 프로필 연결, 역할·부서 투영 | 검증된 신원과 기존 프로필. 이메일을 권한 키로 바꾸지 않음 |
| 계정 회수 | 역할·부서 변경 등의 세션 종료·WebSocket 해제 경로 존재 | 회수 기능을 새로 중복 구현하지 않고 결과·누락 경로 보강 |

NAS ACL 초안 가져오기는 완전히 새로운 아이디어가 아니다. 기존 [NAS-FOLDER-ACL.md](NAS-FOLDER-ACL.md) 10절 결정표 5번에도 1회 수집과 수동 매핑 방향이 있다. 그 미구현 부분을 기업 관리 흐름으로 구체화한다.

### 2.2 지금 사용성이 어려운 근본 이유

1. **관리자가 세 체계를 머릿속에서 연결한다.** NAS 계정·그룹, IX-Auth 계정·그룹, 앱의 역할·부서·폴더 규칙이 각각 보인다. 한 사람의 최종 접근 범위를 한 화면에서 설명하지 못한다.
2. **조직과 권한 묶음이 혼재한다.** 연구개발부 소속과 특정 프로젝트 자료 접근은 다른 사실이다. 부서만으로 표현하면 겸직·공동 프로젝트·외부 협업 때 개인 예외가 쌓인다.
3. **등록된 설정과 실제 가능한 동작이 다르다.** 화면의 `쓰기`, 주체 미리보기, AI 검색 범위가 실제 NAS·런타임 권한과 일치한다는 보장이 아직 없다.
4. **관리 작업의 완료가 흩어진다.** 계정 변경, 그룹 반영, 앱 세션 회수, 검색 차단의 결과가 하나로 보이지 않는다. 일부 성공을 전체 성공으로 읽기 쉽다.
5. **목록의 기준이 통일되지 않았다.** 페이지를 받은 뒤 부서 필터를 적용하고 전체 총계로 다음 버튼을 판단한다. 실측에서 8명만으로도 빈 다음 페이지와 잘못된 누적 인원 표시가 발생했다.

| P1-2 | 사용자 페이지 뒤 부서 필터. 실제 4행에서 다음을 누르면 빈 목록과 `8명 중 25명`. 부서 상세는 첫 100명 요청, 인원수는 로그인 투영 기준 | 이미 데모 규모에서도 페이지 오류 발생. 확장 시 미로그인 직원 누락 가능 | 원본 기준 검색/필터/총계/페이지네이션을 한 소유자로 통일 |
| P1-3 | 부서 변경의 `departmentFailed`가 정상 응답 안에 있고 UI가 별도로 표시하지 않음 | 저장됐다고 생각했지만 일부 소속 미반영 | 완료·부분 완료·실패 구분, 실패한 사람/단계와 재개 동작 표시 |
| P1-4 | 작업 알림을 만든 뒤 상세 재조회에서 알림을 초기화 | 초대 링크·세션 종료 결과가 사라질 수 있음 | 작업 결과 수명을 목록 새로고침과 분리 |
| P1-5 | 유효 역할 목록을 보여주지만 역할 편집은 하나를 골라 전체 교체 | 직접 부여와 그룹 상속의 차이를 이해하기 어려움 | 앱 역할, 직접 역할, 그룹에서 받은 역할을 구분. 영향 검토 후 저장 |
| P1-6 | `쓰기` 선택지는 있으나 현재 NAS 마운트는 읽기 전용. 브라우저 게이트는 hidden 여부만 판정 | 관리자는 쓰기를 열었다고 생각하지만 실패 | 초기 UI에 “연결이 읽기 전용” 표시. 실제 동작별 인가 전 쓰기 활성화 금지 |

특히 P0-1의 현재 테스트는 실제 JSON bulk와 다른 줄 번호를 모킹한다. 테스트가 존재한다는 사실만으로 가져오기를 검증 완료로 처리하지 않는다.

## 4. 목표 권한 모델과 원본 소유권

### 4.1 관리자에게 보여줄 다섯 개념

| 개념 | 뜻 | 예시와 원칙 |
| --- | --- | --- |
| 사용자 | 실제 직원 한 명 | 앱 프로필, IX-Auth 계정, NAS 계정을 연결하되 동일한 이름만으로 병합하지 않음 |
| 부서 | 조직 소속 | 연구개발·품질. 겸직 가능. 폴더 권한을 위해 가짜 부서를 만들지 않음 |
| 접근 그룹 | 자료 접근 목적의 묶음 | 품질문서 열람자, 프로젝트 A 참여자. 여러 부서가 포함될 수 있음 |
| 앱 역할 | 앱 운영 권한 | 직원·관리자 등의 기존 역할. NAS의 administrators 그룹을 앱 시스템 관리자로 자동 승격하지 않음 |
| 자료 원본·폴더 | NAS에서 연결한 업무 자료 | 공유, 하위 경로, 연결 상태, 읽기 전용 여부, 원본 권한과 앱 추가 제한 |

부서와 접근 그룹은 **의미를 분리**하되 새로운 그룹 DB를 즉시 만들자는 뜻은 아니다. IX-Auth에 일반 그룹이 있으므로 우선 재사용 가능성을 확인하고, 분류·외부 매핑·앱 인가 계약에 부족한 부분만 보완한다.

### 4.2 필드별 정본

| 정보 | 권장 정본 | 앱에서 가능한 일 |
| --- | --- | --- |
| 로그인·초대·MFA·앱 계정 상태 | 기존 IX-Auth | 기존 BFF로 관리. NAS 로그인 재사용은 별도 연동 검토 |
| NAS 사용자·그룹·멤버십·원본 ACL | NAS 또는 이미 쓰는 사내 디렉터리 | 읽기 전용 수집, 연결 검토, 동기화 상태 확인 |
| 직원 조직 소속 | 운영자가 정한 조직 정본, 현재는 IX-Auth 부서 그룹 | NAS 그룹과 자동 동일시하지 않고 명시적으로 연결 |
| 앱 역할·AI 사용 범위 | 앱 운영 정책 | 원본 문서 권한을 넓히지 않는 범위에서 추가 제한 |
| 프로필·외부 계정 연결 | Gateway의 명시적 매핑 | 원본 ID, 외부 주체 ID, 검증 상태, 변경 이력 관리 |
| 부서 표시명 | 하나의 명시적 소유자 | 현재 로컬 별칭은 별칭임을 표시. 원본 이름과 조용히 혼용하지 않음 |

목표 불변식은 다음과 같다. **새 정책 제안이며 기존 정책을 알림 없이 대체하지 않는다.**

```text
사용자의 특정 동작 허용
  = 앱 계정이 현재 유효함
  AND 외부 계정 연결이 검증됨
  AND 해당 사용자의 NAS 원본 권한이 그 동작을 허용함
  AND 앱의 추가 정책이 허용함
  AND 서비스 연결 자체가 그 동작을 수행할 수 있음
```

현재 바인드 마운트는 웹 사용자마다 NAS 계정을 바꾸지 않는다. 서비스 계정이 파일을 읽을 수 있다는 사실은 직원 모두에게 읽을 권한이 있다는 뜻이 아니다. 가져온 ACL에 근거한 앱 인가가 필요하고, 스냅샷 방식에는 반영 지연이 있다. 즉시 철회가 요구되면 지속 동기화만으로 충분한지, 요청 시 원본 확인 또는 사용자 신원으로 접근하는 방식이 필요한지 따로 결정한다.

앱 관리 역할과 문서 열람 권한의 분리는 제품 결정이다. 현재 시스템 관리자 우회 동작을 임의로 제거하지 않는다. 향후 일반 관리자는 계정·규칙을 관리하되 기밀 원문 열람은 별도 권한으로 하고, 비상 접근은 사유·범위·이력과 함께 명시적으로 설계하는 안을 검토한다.

## 5. NAS 연동 방법 비교와 권고

| 방법 | 장점 | 한계 | 권고 |
| --- | --- | --- | --- |
| 기존 CSV 초대 + 계정 수동 연결 | 현재 기능 재사용, 첫 직원 도입에 빠름 | 계정 생성만으로 NAS 권한은 연결되지 않음. 현재 행 연결 문제 선행 수정 | 초기 계정 정리용. 임의 비밀번호 복사 없이 초대 흐름 유지 |
| NAS 권한 1회 읽기 → 초안 가져오기 | 기존 ACL을 다시 입력하는 수고 감소, 변경 영향 검토 가능 | 이후 NAS 변경이 자동 반영되지 않음 | **첫 NAS 연동 목표**. “가져옴”과 “동기화 중”을 구분 |
| NAS 읽기 전용 지속 동기화 | 입퇴사·그룹 이동·ACL 변경 추적 | 수집 누락·철회 지연·부분 실패·ID 재사용 처리 필요 | 매핑과 인가 경계가 검증된 후 |
| 기존 AD/LDAP 공용 디렉터리 재사용 | 계정·그룹 중복 관리 감소 | 파일 ACL, 앱 권한, IX-Auth 연동은 별도. 존재 여부 미확인 | 이미 운영 중이면 우선 검토. 도입 일정 때문에 새 디렉터리를 급히 구축하지 않음 |
| 앱에서 NAS ACL까지 양방향 수정 | 관리 화면 한 곳으로 모일 수 있음 | 충돌, 관리자 자격증명, 기존 파일 업무 영향이 큼 | 초기 범위 제외. 읽기 전용 연동 안정화 뒤 별도 결정 |

### 5.1 기존 도구 우선 검토

- **Samba `smbcacls`**: NT ACL 조회, numeric SID, SDDL 출력을 제공하는 기존 OSS 후보다. 임의 ACL 파서를 먼저 만들기 전에 대상 NAS에서 조회 권한·지원 버전·상속·한글 경로를 검증한다. 조회 결과와 권한 평가를 구분하며, ACL 조회가 된다고 모든 직원의 유효 권한 판정이 자동 완성되는 것은 아니다. [Samba 공식 매뉴얼](https://www.samba.org/samba/docs/current/man-html/smbcacls.1.html)
- **Synology File Station API**: 공유·폴더 인벤토리 후보다. 응답의 `perm.acl`은 로그인한 사용자의 권한이므로 관리자 토큰 결과를 직원별 ACL로 복사하지 않는다. 기기의 `SYNO.API.Info`로 실제 API 버전을 확인한 뒤 사용한다. [공식 API 가이드](https://global.download.synology.com/download/Document/Software/DeveloperGuide/Package/FileStation/All/enu/Synology_File_Station_API_Guide.pdf)
- **Synology CLI**: 공식 가이드에 `synouser`, `synogroup`, `synoshare`가 있다. 기존 운영 기록의 `synoacltool -get`은 별도 DSM 종속 후보로 취급하며 안정적인 공개 ACL 내보내기 계약이라고 단정하지 않는다. [공식 CLI 가이드](https://global.download.synology.com/download/Document/Software/DeveloperGuide/Firmware/DSM/All/enu/Synology_DiskStation_Administration_CLI_Guide.pdf)

실측 장비는 DSM 6.2.4-25556 Update 8이다. DSM 6.2는 공식 지원 종료 상태이므로 업데이트 가능성·패키지 호환성·복구 계획을 별도 운영 과제로 기록한다. 이 계획은 NAS 업그레이드를 자동 실행하는 지시가 아니다. [Synology 지원 종료 공지](https://www.synology.com/en-us/products/status/eol-dsm62)

### 5.2 손실 없는 가져오기 절차

```mermaid
flowchart LR
  A[원본 연결 확인] --> B[사용자·그룹·ACL 읽기]
  B --> C[계정·그룹 연결 검토]
  C --> D[허용·회수·충돌 영향 미리보기]
  D --> E[관리자 승인 적용]
  E --> F[사용자별 실제 접근 확인]
  F --> G[변경·실패·철회 상태 추적]
```

1. 연결 원본과 수집 범위를 고른다. 폴더 목록 수집 성공, ACL 수집 성공, 앱 적용 완료는 별도 상태다.
2. `원본 연결 ID + 외부 주체 ID`를 매핑 기준으로 쓴다. SID/UID/GID의 사용 가능성과 삭제 후 재사용을 실제 NAS에서 확인한다. 이름·이메일은 후보 추천만 한다. 이메일 없는 직원, 중복 후보, 비활성·서비스 계정은 검토 대상으로 남긴다.
3. NAS 그룹마다 “부서 연결 / 접근 그룹 연결 / 제외”를 선택한다. 직책·시스템 그룹을 자동 부서나 앱 관리자 역할로 바꾸지 않는다.
4. 원본 ACL의 주체, allow/deny, 상속, 적용 대상, 동작을 보존한다. 파일별 예외·상속 단절·목록/통과 권한을 현재 hidden/read/write로 손실 변환하지 않는다. 표현 불가능한 범위는 **미지원·검토 필요**로 남긴다.
5. 적용 전에 사용자별 추가 허용·회수, 영향 폴더, 충돌, 미매핑 수를 보여준다. 읽기 실패·수집 누락을 원본 삭제로 해석하지 않는다.
6. 재실행해도 중복 계정·그룹·초대가 생기지 않게 한다. 기존 데모 계정과의 연결은 사람이 확인하며 데모를 임의로 실직원 계정으로 승격하지 않는다.
7. NAS에서 가져온 필드는 원본 소유로 표시한다. 앱 예외는 별도 사유와 책임자를 가지며 원본 거부를 덮어쓰지 않는다. NAS에 되쓰지 않는다.

현재 앱의 “깊은 경로 우선, 같은 경로에서 개인 > 부서 > 역할”은 **앱 규칙의 의미**다. NAS ACL 평가 알고리즘으로 그대로 재사용하지 않는다. NAS 동작 평가와 앱의 추가 제한을 결합하는 책임을 명확히 한다.

## 6. 관리 UX 개선안

### 6.1 메뉴 구조

```text
조직 및 접근 관리
  개요          미연결 직원, 미적용 변경, 실패·검토 필요, 마지막 수집
  사용자        검색·필터·등록·초대·계정 상태·최종 접근
  부서          조직 소속과 구성원
  접근 그룹     자료 접근 묶음과 사용자·폴더 연결
  자료 및 폴더  NAS 연결·폴더 트리·원본 권한·앱 추가 제한
  변경 이력     누가 무엇을 바꿨고 어느 단계까지 적용됐는지
```

기존 URL과 페이지는 가능한 한 유지하고 탐색·연결을 개선한다. 채널은 조직 관리와 다른 업무이므로 별도 설정 묶음에 둔다. `/admin/identity/`는 고급 신원 설정 진입점으로 유지하고, 일상 업무는 앱 화면에서 끝낸다.

### 6.2 화면별 필요한 변화

| 화면 | 우선 제공할 정보·동작 |
| --- | --- |
| 사용자 목록 | 이름·부서·앱 역할·상태에 원본/매핑 상태 추가. 초대 대기·미연결·비활성 필터. 상세 열기 동작을 분명히 표시. 대량 작업은 대상 선택과 영향 검토 포함 |
| 사용자 상세 | 기본 정보 / 부서·접근 그룹 / 실제 접근 가능한 폴더 / 세션·변경 이력. NAS 계정과 연결 근거 표시. 첫 로그인 전에도 권한 준비 가능 |
| 부서 상세 | 원본 기준 구성원·총원, 연결된 접근 그룹, 관련 자료. “이 부서에 들어오면 무엇을 볼 수 있나”로 연결. 에이전트 설정은 고급 영역으로 이동 |
| 접근 그룹 | 목적, 원본 NAS 그룹, 구성원, 연결 폴더, 관리자, 예외. NAS 동기화 그룹과 앱 전용 그룹 구분 |
| 폴더 상세 | 왼쪽 검색 가능한 트리, 오른쪽 원본 권한 / 앱 제한 / 사용자 접근 확인 / 변경 이력. 절대 경로보다 공유명·빵부스러기를 우선 표시 |
| 가져오기 | 파일/연결 선택 → 열·계정 매핑 → 충돌 검토 → 적용 → 행별 결과. 단순 텍스트 5줄 미리보기를 서버 검증 결과와 연결 |
| 접근 확인 | 사용자 + 폴더 + 동작 선택. 허용 여부, 근거 그룹, 상속 출처, 원본 버전, 마운트 한계를 설명. 관리 미리보기와 실제 접근을 같은 판정으로 계산 |

사용자 관점 예시: “품질 부서 소속이라 품질문서 그룹에 포함됨 → NAS 읽기 허용 → 앱 읽기 허용 → 최종 읽기 가능.” 거부 시 “앱에서 허용했지만 NAS 원본이 거부”처럼 다음에 고칠 위치가 보여야 한다. 일반 사용자에게는 접근 불가 자원의 이름·상세 근거를 노출하지 않고 관리자에게만 설명한다.

### 6.3 화면 동작 공통화

- 역할 변경처럼 중요한 변경은 선택 즉시 저장과 별도 저장을 혼용하지 않는다. 초안 → 영향 확인 → 저장 → 결과의 흐름으로 통일한다.
- 폴더 이동 시 저장하지 않은 초안이 있으면 저장/버리기/취소를 선택한다. 요청이 늦게 도착해 다른 폴더 결과를 덮지 않도록 선택 식별자를 확인한다.
- “하위에도 적용”은 상속과 하위 예외 삭제를 구분한다. 기본은 기존 예외 보존, 예외 삭제는 삭제될 목록과 영향 확인 후 별도 동작으로 제안한다. 기존 의미 변경이므로 승인·마이그레이션 검토 대상이다.
- 고아 규칙은 전체 삭제만 제시하지 않고 선택 정리와 영향 확인을 제공한다. NAS 일시 단절·권한 조회 실패·실제 삭제를 구분한다.
- 새로고침 후에도 작업 결과를 유지한다. 실패를 빈 목록·정상 0명으로 표시하지 않는다. 부분 성공은 성공·실패 대상을 각각 보여준다.
- 한국어 메뉴와 용어를 통일한다. 제공 화면의 `Folders`는 `자료 및 폴더`로 정리하는 후보이며, 기존 i18n 생성 규칙을 따른다. 테이블 색상 변경만으로 작업을 마감하지 않는다.

## 7. 구현 시 공통화할 소유 경계

| 경계 | 재사용할 현재 자산 | 필요한 정리 |
| --- | --- | --- |
| 신원 조회 | `src/auth/ix-auth/` 클라이언트, claims·역할 해석 | 실제 계정 상태·전체 소속을 반환하는 정본 조회. 로그인 관측 투영과 조직 원장을 구분 |
| 조직 관리 | 사용자·부서 BFF, IX-Auth 그룹 | 사용자 화면과 부서 화면의 멤버 변경을 같은 서비스로 수렴. 단일 역할과 상속 역할 구분 |
| NAS 연결 | 기존 마운트·폴더 수집 | NAS 전용 어댑터가 외부 목록·ACL을 읽고 정규화. UI나 일반 Gateway 코어에 DSM 명령을 흩뿌리지 않음 |
| 권한 판정 | `folder-access-policy.ts`, 경로 정규화 | 앱 정책은 재사용. 원본 ACL 권한과 결합하는 동작별 판정 및 설명 결과를 한 곳에서 제공 |
| 자료 접근 | 브라우저 게이트, 파일 읽기, 검색·미리보기 | 현재 요청자의 검증된 신원과 원본 자료 ID를 전달. UI에서만 숨기거나 검색 결과를 모델에 넣은 뒤 제거하지 않음 |
| 작업 완료 | 기존 관리자 활동 원장, 세션 종료 경로 | 계정/그룹/앱 세션/외부 세션/검색 회수 결과를 명시. 브라우저가 닫혀도 서버가 정리 책임을 가짐 |
| 화면 공통 요소 | 기존 설정 레이아웃, 테이블, 알림, 역할 라벨 | 주체 선택기, 권한 설명, 변경 미리보기, 단계별 결과를 실제 중복이 있는 곳부터 공통화 |

새 인증 서비스, 별도 범용 권한 엔진, 새 디자인 시스템을 먼저 도입하지 않는다. 외부 그룹을 담는다고 IX-Auth와 Gateway 양쪽에 독립된 조직 원장을 하나씩 추가하지 않는다. IX-Auth 계약을 바꾸어야 한다면 [ix-auth/MODULE.md](../ix-auth/MODULE.md)의 원본 계약 절차를 따른다.

**기존 IX-Auth L2도 재사용 검토 대상이다.** 실제 콘솔에는 USER/ROLE/GROUP, ALLOW/DENY, file 리소스, 위임 판정 기능이 이미 보인다. 그러나 현재 앱 폴더 규칙과 저장·판정 의미가 같다고 볼 수 없다. 우선 두 판정기의 호출자·상속·deny·관리자 우회·경로 정규화·회수 계약을 비교한다. 기존 앱 정책을 정본으로 유지하면서 L2 화면의 적용 범위를 명시할지, L2를 정본으로 수렴할지는 설계 결정으로 남긴다. 두 곳을 동시에 편집하고 일부만 반영되는 이중 원장은 만들지 않는다. 콘솔의 “앱이 물어서 판정” 문구만으로 현재 Gateway가 해당 API를 호출한다고 간주하지 않는다.

### 7.1 AI 자료 접근까지 이어지는 완료 기준

- 브라우저 목록·다운로드·미리보기, 파일 도구, 검색 결과·인용, 모델에 전달되는 본문이 같은 사용자·자료 권한을 사용해야 한다.
- 색인 시 수집 허용 여부와 질문 시 열람 권한은 별개다. 공용 색인을 쓰더라도 모델 입력 전 사용자별 인가가 필요하다. 사용자별로 파일을 복제하는 방식을 기본안으로 삼지 않는다.
- 검색 청크·변환본은 원본 자료 식별자를 유지한다. 경로 변경·원본 삭제·권한 회수 후 캐시와 인용 링크도 현재 권한을 다시 검사한다.
- 실행자는 세션 생성자나 감사 기록에서 추정하지 않는다. 실제 요청의 검증된 신원을 전달하고, 위임·예약·채널 등 신원 없는 경로는 별도 정책을 갖는다.
- 철회 시 이미 전송된 답변을 되돌릴 수는 없다. 새 조회·새 출력과 진행 중 작업의 공개 직전에 재확인하는 경계를 정한다. 기존 대화·내보내기·공유 링크의 보존 및 접근도 함께 설계한다.
- 원본 권한 수집 실패·만료 시 해당 자료의 신규 접근/허용을 어떻게 제한할지 결정한다. 서비스 전체를 무조건 중단하는 대신 영향 범위와 복구 방법을 표시한다.
- 원장·매핑·동기화 상태 등 새 영속 데이터가 필요하면 기존 SQLite 소유권과 마이그레이션을 먼저 설계·승인한다. 임시 JSON 사이드카를 새 권한 원장으로 만들지 않는다.

## 8. 실행 순서와 범위

첫 사용일이 9월 14일 월요일이라면 완성형 동기화를 출시 약속으로 잡지 않는다. 아래 일정은 **작업 순서**이며 인력·권한·장비 실측 결과에 따라 산정한다.

| 0. 범위 확정 | 실제 인원, 계정 원본, NAS 정리 상태, 공용/민감 자료, 관리자 역할 결정. 대표 계정과 폴더 선정 | 플랫폼·관리 화면 실측은 1.1절 완료. 다음은 직원-계정-폴더 기대 권한표 합의와 이미지의 Git SHA 연결 |

3~5단계는 설계상 함께 맞물린다. 계정·그룹/자료 ID 계약을 먼저 공유하고, **UX가 만들어졌다는 이유로 제한 자료까지 공개하지 않는다.** 출시 전 수정이 끝나지 않으면 소수 실직원 계정을 개별 검증하는 공용 자료 파일럿으로 범위를 줄이는 안을 선택한다.

민감 자료 제외는 NAS 마운트만 빼는 것으로 끝나지 않는다. 기존 변환본·검색 DB·캐시·대화에 남은 자료도 범위를 확인하고, 정리 작업은 운영 승인과 증거를 남긴다. 사용자 요청 없이 데모 계정이나 기존 자료를 삭제하지 않는다.

## 9. 검증과 도입 판정

현재 포크 검증 방식에 맞춰 Actions와 실제 배포 검증을 사용한다. 검증 데이터는 합성 이름·문서로 만들고 실제 직원 비밀번호를 공유하지 않는다. 이 문서는 검증 계획이며 아래 항목을 이미 통과한 것으로 표시하지 않는다.

| 시나리오 | 기대 결과 | 필요한 단계 |
| --- | --- | --- |
| 다른 부서 2명의 CSV, 실패 행·빈 줄 포함 | 응답과 부서가 같은 사람에 연결, 성공/실패/초대 결과 구분 | 출시 전 |
| 등록했지만 로그인하지 않은 직원 | 목록·부서 총원·권한 준비에 나타남 | 출시 전 |
| 25명 초과 목록, 100명 초과 합성 부서 | 필터 총계와 모든 페이지 정합성 | 목록 수정 검증 |
| 원본 구성원 API 실패 또는 부서에 미로그인 구성원 존재 | 빈 부서로 삭제하지 않음, 확인 실패 표시 | 출시 전 |
| 부서 변경 중 일부 외부 API 실패 | 완료로 오인하지 않음, 반영·미반영 범위와 재개 방법 표시 | 출시 전 |
| 초대 재발송·세션 종료 후 새로고침 | 결과가 남고 다음 동작 가능 | 출시 전 |
| 직원/관리자/시스템 관리자 각각의 읽기 | 합의한 관리 역할과 문서 권한 그대로 동작 | 출시 전 |
| 거부된 문서 이름·고유 문자열로 검색/질문 | 제목·본문·인용·다운로드에서 노출되지 않음 | 제한 자료 공개 전 |
| 다중 그룹 allow/deny, 개인 예외, 상속 차단, 파일별 ACL | 실제 NAS 결과와 앱 결과 일치 또는 미지원 표시 | NAS 연동 전 |
| NAS는 거부, 서비스 계정은 읽기 가능 | 해당 직원의 앱 접근은 거부 | NAS 연동 전 |
| 이름 변경·삭제 후 같은 이름 재생성, 이메일 없음 | 자동 오연결 없음, 확인 필요 표시 | NAS 연동 전 |
| 부서 이동·계정 비활성·NAS 권한 회수 | 기존 WebSocket·신규 요청·실행 중 출력·검색·캐시에서 회수 계약 준수 | 제한 자료 공개 전 |
| 수집 중 단절·부분 목록·권한 부족·재시작 | 대량 삭제/권한 확장 없음, 마지막 완료와 실패 구분 | 지속 동기화 전 |
| 저장 안 한 폴더 초안, 늦은 응답, 하위 예외 정리 | 엉뚱한 폴더 저장·초안 유실·조용한 예외 삭제 없음 | UX 수정 검증 |

출시 통과의 기준은 “화면이 열린다”가 아니라 **등록한 직원이 허용 자료로 질문하고, 비허용 자료는 모든 경로에서 막히며, 관리자가 그 결과를 설명하고 회수할 수 있다**이다. 실측에는 배포 SHA, 계정 역할, 합성 문서, 수행 시각, 기대/관측 결과를 남긴다. 이미지 빌드 성공과 비차단 `chris-check` 성공은 각각 확인한다.

운영 UX의 초기 목표: 관리자는 직원 등록→소속 연결→접근 확인을 화면 간 ID 복사 없이 끝내고, 권한 문의는 사용자와 폴더 선택만으로 원인을 찾는다. 작업 시간 목표는 첫 사용자 관찰 후 정하며 지금 임의의 성능 수치를 완료 보장으로 두지 않는다.

| 관리자 열람 | 계정 관리 권한과 자료 열람을 구분하는 방향 | 기존 관리자·임원·시스템 관리자 접근 변경 승인 |
| 동기화·철회 | 초기 수동 승인 적용, 이후 지속 수집 | 허용 지연, 긴급 회수 담당, 원본 장애 시 자료별 동작 |
| 저장·계약 | 기존 소유자 재사용, 필요한 최소 확장 | 새 SQLite 스키마/영속 의미·설정·IX-Auth 계약 변경 승인 |

미결정이 있어도 기존 소스 불일치 재현, 화면 설계, 대표 ACL 조사 계획은 진행할 수 있다. 새 권한 의미·원본 쓰기·DB 설계는 이 문서만으로 승인된 것으로 취급하지 않는다.

## 11. 단계별 진행 기록

### 11.1 1단계 "첫 도입 전 정확성" 코드 수정 (2026-09-11)

8절 1단계 가운데 코드로 해결되는 항목을 `chris/main` 에 넣었다. 커밋 해시는 [DELIVERY-PLAN.md](DELIVERY-PLAN.md) 5절 AB 행에 있다. 운영 실측은 Actions 이미지 반영 뒤 별도로 기록한다.

| ID | 수정 내용 | 검증 |
| --- | --- | --- |
| P0-1 | 게이트웨이가 IX-Auth JSON bulk 결과를 줄 번호가 아니라 **배열 위치**로 원본 행에 연결하고, 이메일이 같은지 확인한 뒤에만 부서를 붙인다. 응답의 줄 번호는 스프레드시트 기준(헤더 포함 2부터)으로 되돌려 주고, 행마다 `departments.granted`·`departments.failed` 를 싣는다. 가져오기 화면은 "계정은 생겼지만 부서가 안 붙은 줄" 을 줄 번호·이메일·부서 코드로 나열한다 | 테스트를 실제 계약(1부터)으로 고쳤고, 두 사람이 서로 다른 부서로 들어가는 사례와 이메일 불일치 시 부여하지 않는 사례를 추가했다 |
| P0-3 | IX-Auth 벤더 트리에 계약 표에는 있으나 구현이 없던 `GET /admin/groups/{id}/members` 를 넣었다(`ix-auth/MODULE.md` 6절 델타). 게이트웨이의 부서 삭제는 그 GET 이 실패하면 사용자 목록 전체를 걸어 세고, 그것도 실패하면 로그인 투영으로 대체하지 않고 503 `member_count_unavailable` 로 거부한다. 부서 목록의 인원수도 신원 서버 목록 기준이며, 응답에 `memberCountSource` 로 출처를 밝히고 화면은 투영 기준일 때 안내문을 띄운다 | Java 는 로컬에서 `compileJava` 통과. 게이트웨이 테스트에 405 후 스캔 대체, 둘 다 실패 시 503, 목록 인원수 원본 기준·투영 대체 사례를 추가했다 |
| P1-2 | 부서 필터가 켜지면 게이트웨이가 신원 서버 목록을 100건씩 끝까지 읽어(상한 50페이지) 부서로 거른 뒤 페이지를 자른다. 총계·페이지가 부서 기준이 되고 "8명 중 25명" 같은 표시가 사라진다. 화면의 "현재 페이지에만 적용" 안내문은 제거했다. 부서 상세는 100명을 넘으면 "앞 100명만 표시" 안내를 띄운다 | 300명·3페이지 합성 목록에서 부서 100명·2페이지째 25명·시작 인원 확인 테스트 |
| P1-3 | 부서 변경 응답에 `failedDepartments` 와 실제 반영된 `departments` 를 싣는다. 사용자 상세와 부서 화면 모두 부분 반영이면 실패한 부서를 이름으로 알린다 | 기존 부서 변경 테스트 유지. 화면 문구 en·ko 추가 |
| P1-4 | 사용자 상세에서 동작 뒤 재조회할 때 결과 알림을 지우지 않는다. 다른 행을 고를 때만 지운다 | 코드 경로 확인. 브라우저 실측은 배포 후 |

하지 않은 것: P1-1(실제 사용자 유효 권한 검사), P1-5(직접 역할과 상속 역할 구분), P1-6(읽기 전용 표시), 3~5단계 전부. 새 저장소 스키마·설정·IX-Auth 계약 변경은 없다. P0-3 의 Java 변경은 계약 변경이 아니라 계약대로 구현한 것이다.
